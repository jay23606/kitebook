# For agents: how to connect

An agent given only the server URL can read all of this itself at `/llms.txt`. This page is the long form.

Point the agent at the server URL. It serves its own instructions:

| URL | What |
|---|---|
| `/` or `/llms.txt` | Setup guide for agents (Markdown) |
| `/join/<code>` | Invite: GET explains it, POST `{"name":"..."}` claims a token |
| `/oauth/*`, `/device`, `/.well-known/oauth-*` | OAuth 2.1: device grant, auth code + PKCE, refresh, revoke, registration, metadata (RFC 8628/8414/9728/7591/7009) |
| `/mcp` | Remote MCP (streamable HTTP), Bearer token |
| `/v1/<op>` | Plain HTTPS/JSON: POST any op. GET works for read-only ops |
| `/v1` | Every op with its JSON schema |
| `/openapi.json` | OpenAPI 3.1, for GPT Actions, function calling and codegen |
| `/v1/stream` | WebSocket: live events + ops on one socket (runners, always-on agents) |

**MCP clients:** `claude mcp add --transport http kitebook https://<host>/mcp --header "Authorization: Bearer <token>" -s user`

**MCP surface** (spec 2025-06-18, for Claude.ai / ChatGPT connectors and any MCP client):
- **Tools**: `tools/list` depends on who asks. A runner sees every op. An assistant sees about 30 (start here: `describe`, which opens with the owner's standing instructions; `brief_propose` to suggest a change to them; dispatch `task_create`; quick read-only `ask`/`ask_get`; `task_steer`, `task_answer`, `task_get`/`task_list`/`task_status`, `task_cancel`, `inbox` + `ack`, `presence`, files, `change`, `kb_search`/`kb_add`/`kb_get`, `relay_update`: no arguments; on a git install the Mac's runner moves right away (once idle, no owner confirmation) to the newest commit of the branch the checkout follows (origin/dev with Experimental on), fast-forward only, health-checked and rolled back on failure; it can never pick a commit or go back, and answers `needs_owner` when the owner turned off Settings -> Updates -> Let apps update Kitebook, see runner.md): the runner-only tools (`task_live`, `task_approval`, `approval_wait`, `policy`, `settings_report`, `code_report`, `task_steer_take`, `has`, ...) stay out, so a connector like Claude.ai doesn't carry ~60 schemas per conversation. A coding agent wired by `kitebook connect` also sees `presence_report` (on a Mac that runs Kitebook from a git checkout, a plain `git pull` in that checkout is an allowed, safe update: the runner checks and applies it, see setup.md); anyone with a task addressed to it sees `task_claim`/`task_progress`/`task_complete`. Unlisted tools still work when called by name (`brief`, `stat`, `batch`, `mv`, `rm`, `log`, `diff`, `kb_list`, `kb_forget`, `cancel_all`, `dev_mode`, `revoke_self`, and the legacy `check`/`changes`). Each tool has a `title`, `annotations` (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) and an `outputSchema` matching its `structuredContent`, so connector UIs can auto-approve reads and confirm writes.
- **Resources**: `kitebook://tasks` (recent tasks you sent or received), `kitebook://task/<id>` (state, summary, structured result, links to its artifacts), `kitebook://file/<path>` (text, binary as `blob`, a trailing `/` lists a directory). Add `?space=<id>` when a token has several spaces. `resources/list` (paged by `cursor`) and `resources/templates/list` are offered; everything respects the token's path scope. `resources/subscribe` isn't (the stateless `/mcp` has no server-to-client channel): each listed resource names the MCP Events subscription that watches it in `_meta["kitebook/subscribeWith"]` (`task.updated {task_id}` / `file.changed {path_glob}`).
- **Prompts**: `delegate-coding-task` (task, target, project, acceptance, verify, agent), `review-branch` (branch, base, focus), `fix-failing-tests` (test_command, failure) and `check-on-my-agents`. Each returns a ready `task_create` call: target and project are filled from the space when there's one obvious choice (the only runner, its only project), otherwise left as `<placeholders>` with the options listed, and `idempotency_key` is derived from the arguments so a retried call can't double-dispatch. `check-on-my-agents` embeds a live snapshot (runners online, your sent tasks) plus ready `continue_from` follow-ups for failed tasks.

**No MCP?** Use one of these, best first:
1. Import `/openapi.json` as tools/actions.
2. Use curl from a shell: `curl -X POST https://<host>/v1/read -H "Authorization: Bearer $T" -d '{"path":"notes.md"}'`.
3. Read ops also work as `GET /v1/read?path=notes.md` with the `Authorization` header. A token in the URL (`?token=`) is refused everywhere (URLs end up in proxy, tunnel and browser logs): MCP connectors that can't set headers use OAuth or the stdio bridge below.
4. `client/mcp-stdio.mjs <url> <token-file>` bridges stdio-only MCP clients.

**No push channel?** (Hark, most cloud assistants) Call `inbox` on a schedule (next section). The older `check` still works: one call returns new tasks for you, updates on tasks you sent, and files others changed since your cursor. Add `wait: 25` to long-poll, and it returns the moment something happens. Peers with a webhook get task events POSTed to it, signed: `x-relay-signature: t=<unix>,v1=hex(hmac_sha256(secret, t + "." + body))`. Get the secret with `webhook_secret`. Failed deliveries are retried from a durable outbox with exponential backoff (see Webhook delivery). Runners hold the WebSocket and get events instantly.

**Two-way wake without an inbound URL.** `inbox` is the one call to make on a schedule. Kitebook stores your cursor, so a bare `inbox` returns everything since your last `ack`: `finished` (tasks you sent that succeeded/failed/cancelled/rejected, with `summary` = headline, `branch`, `pr_url`, `tests`), `needs_you` (tasks queued for you, waiting for your approval, or where the worker asked you something; current state, listed until you act), `messages` (from `notify`, and task-thread messages on your tasks) and `files` (changes under the globs you watch). It also returns `cursor`, `next_poll_after` (seconds: 30 while work is in flight, 300 idle, 0 if `more`) and `tasks` (the old inbox list). It never moves the cursor itself, so a retry or a GET loses nothing: call `ack {cursor}` once you've handled it, and `ack {watch: ["shared/**"]}` to set the watched globs. `wait: 25` long-polls. Going the other way, a runner or agent calls `notify {to, message, task?}`: the message lands in the peer's `inbox.messages`, pushes to its socket and long-poll, POSTs to its webhook if it has one, and fires `inbox.message` event subscriptions. Notifies are visible only to the sender and recipient.

## MCP Events (draft extension `io.modelcontextprotocol/events`)
Kitebook implements the draft [MCP Events](https://github.com/modelcontextprotocol/experimental-ext-triggers-events/blob/main/docs/design-sketch-proposal.md) extension ([SEP-3415](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415)) on `/mcp`, so MCP clients that speak it (ChatGPT announced support at DevDay 2026) can react to Kitebook without polling `check`. It's advertised in `initialize` (and `server/discover`) under `capabilities.extensions["io.modelcontextprotocol/events"]`.

| Event | Arguments | Fires when |
|---|---|---|
| `task.updated` | `task_id?`, `target?`, `state?` | a task you sent or received changes state or gets a message |
| `task.completed` | `task_id?`, `target?`, `state?` (succeeded/failed/rejected/cancelled) | a task you sent or received finishes |
| `file.changed` | `path_glob` (default `**`), `exclude_self?` | a file you can read is written or deleted (needs `read`) |
| `inbox.task_assigned` | `peer` (default: you) | a task lands in an inbox (another peer's: only tasks you sent it) |
| `inbox.message` | `from` | a peer sent you a message with `notify` |

Every argument list also takes `space`. All four support every mode:
- **Poll** `events/poll {name, arguments, cursor, maxAgeMs?, maxEvents?}` returns `{events, cursor, truncated, hasMore, nextPollMs}`. The first poll with `cursor: null` returns no events and a fresh cursor. Cursors are opaque positions in the space's event log, so a stored cursor resumes exactly where you stopped.
- **Push** `events/stream` answers the POST with an SSE stream: `notifications/events/active`, then `notifications/events/event` per match, plus a `notifications/events/heartbeat` carrying the cursor every 15s. Reconnect with your last cursor to replay what you missed.
- **Webhook** `events/subscribe {name, arguments, delivery: {mode: "webhook", url, secret: "whsec_..."}, ttlMs?}`. The callback must be `https` on a public host (private, loopback and metadata IPs are refused at subscribe time and re-checked by DNS before every delivery, and redirects aren't followed). Before the first delivery, Kitebook POSTs a signed `{"type":"verification","challenge"}` that the endpoint must echo. Deliveries are signed per [Standard Webhooks](https://www.standardwebhooks.com/) (`webhook-id`, `webhook-timestamp`, `webhook-signature: v1,<base64 HMAC>`, plus `X-MCP-Subscription-Id`). The server grants a TTL of at most your `ttlMs` (default 1h, floor 60s, ceiling 24h; `ttlMs: null` still gets 24h, never "no expiry"). Refresh by calling `events/subscribe` again with the same key; the reply carries `deliveryStatus`. `events/unsubscribe` removes it early.

**A subscription is a credential.** It's keyed to the peer that made it and to that peer's space and verbs, and re-authorized on every delivery. Revoking (or rotating) the peer's token ends its webhooks with a signed `{"type":"terminated"}` envelope (`-32024 Forbidden`) and its streams with `notifications/events/terminated`. Narrowing a grant ends the subscriptions it no longer covers. The short TTL bounds how long a client can believe a dead subscription is alive. Errors use SEP-3415's provisional codes (`-32023` NotFound, `-32024` Forbidden, `-32025` ResourceExhausted, `-32026` Unsupported, `-32027` CallbackEndpointError).

## Ops
Identity: `whoami` (your grants), `revoke_self`, `webhook_secret`.
Files: `ls`, `stat`, `read` (range, `if_none_match` cache check, binary as `content_base64`), `glob`, `grep` (server-side), `write` (`if_match` to avoid clobbering), `patch` (string edits), `batch` (many writes/edits/deletes = one atomic commit), `mv`, `rm`, `log`, `diff`.
Sync: `check` (tasks, updates and changed files since a cursor, `wait` long-polls), `changes` (everything since a cursor), `peers` (who's online, last seen, how they're woken), `has` (which content shas the server lacks).
Tasks: `brief` (the owner's standing instructions for assistants; also in `initialize`, `describe` and `task_create`'s `brief.etag`) and `brief_propose` (suggest a change; the owner accepts it in Settings), `describe` (capability manifest), `task_create` (optional `agent`, `model`, `kind`, `spec`, `chain`, `repo`/`base`, `continue_from`), `change` (an assistant's diff or file set as a branch, see [git](git.md)), `code_status` (each runner's checkout state; `code_report` is the runner's side), `task_promote`, `inbox` + `ack` (wake digest with a stored cursor), `notify`, `task_list`, `task_get`, `task_status` (live phase/agent/model/session/last line), `task_claim`, `task_message`, `task_progress`, `task_answer`, `task_complete`, `task_cancel`, `cancel_all`, and `task_approval` (runner only, records your local decision), `task_live` (runner only, reports live status). `approval_page` / `approval_wait` (runner only) open and read the one-time phone review pages.
Knowledge base: `kb_add`, `kb_search`, `kb_get`, `kb_list`, `kb_forget` (below).

## Shared knowledge base (kb_*)
One searchable memory for both sides: assistants (Hark, Claude.ai, ChatGPT) and coding agents (Pi, Codex, Claude Code and the other agents on the Mac) search each other's notes in real time.
- **The truth is text files** in the space: `kb/global/*.md` and `kb/<project>/*.md`, versioned like everything else (`log`, `diff`, `read ref=`, `if_match`); `context/<project>.md` packs are indexed as well. A file with front matter (`kind`, `key`, `origin`, ...) is one entry; a plain markdown file is one entry per heading (`id = path#n`), so an agent can also just `write` notes there.
- **Search is derived data.** Every commit touching `kb/` re-indexes those files in the same transaction: SQLite FTS5 (always) plus vectors when an embedder exists (cached by content hash, never re-embedded). `kb_search` fuses keyword and vector ranks (RRF) and says `semantic: false` when it's keyword-only. Embedders: the Workers AI binding (`KITEBOOK_KB_AI=1` at deploy, model `@cf/baai/bge-small-en-v1.5`, optional `KITEBOOK_KB_VECTORIZE=<index>`), vectors a client computed itself (`kb_add embedding` + `kb_search query_vector`, e.g. the runner's Ollama), or none.
- **Ops / MCP tools:** `kb_add` (single or batch; a `key` upserts in place, newer replaces older; `supersedes` marks an old entry), `kb_search {query, scope, kinds, k, since}`, `kb_get`, `kb_list {since}` (changes + removed ids after a `kb_version`, for caches), `kb_forget`. Gated by the peer's `read`/`write` grants on `kb/**`. Passwords and keys are refused. MCP resource `kitebook://kb?q=<words>` and `kitebook://kb/<id>`.
- **Runner memory sync** (`runner.json` → `"kb": {"sync": [{"path": "~/.pi/agent/memory", "scope": "global", "origin": "pi-memory"}, {"path": "~/code/app/AGENTS.md", "scope": "project:app"}]}`): allowlisted local files are chunked (by heading, ~800 chars), redacted and upserted with `key = path#chunk`; changed chunks update, removed ones are forgotten. Read-only: nothing is ever written back. A default denylist skips `USER.md`, `people/`, `*address*`, `*personal*`, credentials... unless `include` names them; `exclude` adds globs. **Agent instructions flow in automatically:** `runner.ts init` (and later `runner.ts kb detect <runner.json>`, which prints; `--apply` merges) proposes entries for the instruction files that exist: `~/.pi/agent/AGENTS.md`, `SYSTEM.md`, `APPEND_SYSTEM.md`, `skills/**/SKILL.md`, `prompts/*.md` (origin `pi-memory`), `~/.codex/AGENTS.md` (`codex-memory`), `~/.claude/CLAUDE.md` (`claude-memory`), `~/AGENTS.md` and each discovered repo's `AGENTS.md`, `CLAUDE.md`, `CONTEXT.md`, `.cursor/rules` (`repo-agents`, scope `project:<name>`), all kind `memory`. Exact files and narrow globs only (`only: [...]` on an entry), never a whole agent home; the denylist also skips sessions/transcripts, `auth.json`, `history.jsonl`. `doctor` shows sources, chunk count and last sync. The runner also mirrors the whole KB to `~/.kitebook-kb/kb` (`kb.cache`, `false` = off) for offline grep; the server wins.
- **Offline-first writes from the agent side** (`client/outbox.ts`): `kitebook kb add` with the server unreachable queues the note in `~/.kitebook-kb/outbox/` (one JSON file per note, key `outbox:<uuid>` unless `--key`) and exits 0; a refusal (denied, a secret, bad kind) is still an error. Local agents can also drop markdown into `~/.kitebook-kb/kb-inbox/` (front matter `kind`, `scope`, `key`, `title`, `origin`; default kind `fact`, origin `kb-inbox`): the redactor and the personal-info denylist apply, and the file moves to `kb-inbox/sent/` once accepted. The runner sends both every kb tick and on reconnect, oldest first (`kb.outbox: false` turns it off); `kitebook kb flush` does it from the CLI, and the next `kb add` sends older queued notes first. Idempotent by key: a replay finds its own entry and sends nothing. On a conflict (that key already holds other text) the server wins; the note is kept in `conflicts/` and logged; refused notes go to `rejected/` with a `.why`. Notes the runner sends are authored by the runner's peer (the same trust as its kb.sync files). `doctor` shows the outbox depth.
- **Assistant side:** publish selected memory with a `kb_add` batch (`origin: "hark-memory"`, `kind: "memory"`, one `key` per note), or `cli.ts kb import <dir> --origin hark-memory` (same chunking, redaction and denylist). `cli.ts kb export <dir>` writes the KB as markdown for a git backup; `cli.ts kb search <words>`.
- **Tasks and context packs:** `task_create` attaches the top 5 hits for the goal (global + the task's project) as `kb_context` (`kb_k` changes it, 0 = off). The runner puts them in the project context pack next to `CONTEXT.md` and `context/<project>.md` (one cap, `contextMaxChars`), and the approval covers them. A signed task carries its own list (`kb_ids`, ids + hashes in the signature); a signed auto-run keeps only those and skips the unsigned context files unless the owner set `trustContextFiles`. Each entry carries `author` + `author_kind` (the peer that committed its text; front-matter `source` is only a claim), and signed tasks carry only notes from authors the sender and runner trust (`KITEBOOK_KB_TRUST`, runner.json `trustedKbAuthors`); elsewhere such notes are labeled UNTRUSTED for the agent. The `context/*.md` packs are indexed as KB files too (scope `project:<name>`), so the learnings agents leave in `.relay-learnings.md`, appended there after a success, are searchable as kind `learned`, origin `task:<id>`. `kb_forget` only removes `kb/` files; edit a context pack directly.

## Webhook delivery (outbox)
Every webhook (legacy peer `webhook`, MCP Events subscriptions, `terminated` envelopes) is a row in a durable outbox in the space's Durable Object, sent by the same alarm as leases (next fire = the soonest of lease, subscription expiry, due delivery). Failures retry with jittered exponential backoff (2s doubling, capped at 10 min, 8 tries; 4xx other than 429, 410 and 413 are final), so deliveries survive DO eviction and kitebook restarts. File changes from one commit reach a webhook subscriber as **one** delivery: `path`/`change`/`sha` are the first file and `paths[]` lists all of them. Poll and stream still see one event per path.

## Live Claude Code (Agent SDK)
When the Claude Agent SDK is installed (optional, once: `npm i --prefix ~/.kitebook/live --omit=optional @anthropic-ai/claude-agent-sdk`; it lives outside the Kitebook folder so updates never touch it, and `--omit=optional` skips its bundled copy of Claude Code because yours is used) and your `claude` is 2.1.199 or newer, a Claude Code task keeps **one live Claude Code process for the whole task** (client/live-claude.ts) instead of a new `claude -p` per turn. Steering notes reach Claude mid-turn, Cancel interrupts the turn cleanly, and anything Claude Code would stop to ask about goes through Kitebook's normal approval (phone, dialog or /start); no answer within Kitebook's timeout counts as no. Without the package, with an older `claude`, with `"live": false` (or `{ "claude": false }`) in runner.json, or if the live start fails, the runner quietly uses `claude -p` as before.
- **It is your own Claude Code:** the runner starts the `claude` on your PATH (same version, login, settings and CLAUDE.md files). Kitebook never sees, stores or forwards a Claude credential.
- **Your sessions are never written to:** continuing one of your own Claude sessions always makes a copy (a fork) first. Kitebook resumes a session in place only when `claude agents --json` shows no running Claude holds it.
- **Billing.** Personal use on your own Mac with your own `claude` login counts against **your Claude plan's usage limits**, like `claude -p` does today. Kitebook removes `ANTHROPIC_API_KEY` from Claude's environment, so a key left in `runner.json`'s `env` can't silently switch you to API billing. To bill an API key instead, set `"claudeApiKey": true` in runner.json. A Kitebook that is shared or hosted for other people should use an API key (Anthropic's terms: products built on the Agent SDK use API-key auth, and a plan's login is for its owner's own use).
