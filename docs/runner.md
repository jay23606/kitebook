# The Mac runner

Reference for the runner (`client/runner.ts`). Installing it is one line from `/start` (see the [README](../README.md#quick-start)).

## Run the runner on your Mac
`client/runner.ts` dials out over one WebSocket, so no ports are opened. When a coding task arrives, it asks you locally (a macOS dialog or the terminal). If you approve, it runs your configured agent (Pi/Codex) in a fresh git worktree on branch `kitebook/<task-id>` of an allowlisted project, then runs the allowlisted verify command. It uploads the diff, a `git format-patch` file (apply anywhere with `git am`), the test log, `git.json` (branch, base, commit) and a summary. You can cancel from either side.

**First run, no hand-editing:**
```bash
bun client/runner.ts init https://<kitebook> https://<kitebook>/join/inv_xxx [--name mac] [--roots ~/code,~/work] [--phone]
bun client/runner.ts install ~/.kitebook/runner.json     # macOS: the command init prints as "next"
kitebook doctor                                                # anytime: url, token, space, agents on PATH, projects, approvals (probes the ntfy server), launchd, runner integrity
kitebook doctor --test-push                                    # same, plus one test notification to your phone
```
`init` claims the invite (use one with `read,write,delete,dispatch` on `tasks/** shared/** repos/**`), finds installed agents (pi, codex, claude; the first becomes the default), discovers git repos under `~/code ~/src ~/projects ~/dev` (or `--roots`), and writes `~/.kitebook/runner.json` at mode 600 with safe defaults: `approve` dialog on macOS, `browser` elsewhere (you approve on the server's `/start` Status card or with `kitebook approve` on that computer; no push through the public ntfy.sh), phone with a fresh ntfy topic only with `--phone`, `access` worktree, push never, 2 agents at once. It refuses to overwrite an existing config (`--force`). `set runner.json roots ~/code,~/work` changes where repos are found.
Before claiming the invite, `init` installs the server's runner as a pinned version (below) and prints its `next` commands from `~/.kitebook/current/` (`--no-install` keeps running from where you are).

### Runner integrity
The runner never runs from a checkout someone can push to. The server serves `/runner-files/manifest.txt` (`sha256  name` per client file, `sha256sum -c` format); the first 16 hex of the manifest's own sha256 is the runner **version**, so a version name pins every byte. `install.sh` (which embeds the version it expects) and `init` download each file, check it against the manifest, and only then install it read-only (files 0444, dir 0555) into `~/.kitebook/versions/<version>/`, with `~/.kitebook/current` pointing at it (launchd starts `current`; `~/.kitebook/client` links there for older plists). A different manifest or a file whose sha256 differs is refused and nothing changes. `doctor` re-checks the installed copy and names any changed, missing or extra file, with the fix: rerun `curl -fsSL https://<kitebook>/install.sh | sh` (no invite needed once runner.json exists; it keeps it). The install dir is covered by `protectedFiles`, so an agent that edits its own runner (or repoints `current`) fails its task. Updates go through `service ... update` below.

### Signed releases
The manifest is only as trustworthy as whoever serves it, so releases are also signed: the **release key** (Ed25519) signs the manifest offline and the server serves the signature as `/runner-files/manifest.sig` (one line, `ed25519:<public key> <signature>`, base64url, over `relay-runner-manifest:v1\n` + manifest.txt). The public key is pinned in `client/release-key.ts`, which ships inside every runner (and is itself a signed file), and the server embeds it in `install.sh`. With a key pinned, `install.sh`, `init` and `service ... update` refuse an unsigned or badly signed manifest **before downloading a single runner file**, and the key that checks an update is always the one already installed, never one the new version brings. The installed copy keeps its `manifest.sig`; `doctor` re-checks it (`release signature: ...`) and the runner refuses to start on a bad one. With no key pinned (a legacy install) everything still installs, with a warning.
- Sign a release (no file to open, no value to copy): `kitebook release-key create` once makes the Ed25519 release key, keeps the private half in your OS secret store (macOS Keychain, libsecret on Linux, else `~/.config/kitebook/release-key.json` at 0600) and, run in your Kitebook checkout (or with `--repo <dir>`), pins the public half into `client/release-key.ts` for you (Settings -> Releases -> Create release key asks your Mac's runner to do the same, so the private key never leaves the Mac). `kitebook release-key show` prints the public key and fingerprint; `kitebook release-key rotate` replaces the key and re-pins it. Then after every change to `client/`: `kitebook release sign` (writes `release/manifest.sig`, which Kitebook bundles) and deploy. `bun scripts/sign-release.ts check` tells you whether the committed signature still matches `client/`.
- Self-hosting with your own key: deploy with `KITEBOOK_RUNNER_RELEASE_KEY=ed25519:...` (embedded in your Kitebook's `install.sh`) and either commit your `release/manifest.sig` or pass it as `KITEBOOK_RUNNER_MANIFEST_SIG`. On a Mac, `KITEBOOK_RELEASE_KEY=ed25519:...` (install.sh / `init --release-key`) pins a key at install time and `init` stores it as runner.json `"releaseKey"` (owner-only; it wins over the built-in key). The first install still trusts the `install.sh` you ran; every update after it is held to the key you pinned.

### Safe updates
Updating to the newest **official signed release** needs nobody's y, because nobody picks the code: the only release that installs by itself is one signed with the release key this Mac already pinned (install.sh pins the server's key at install, stored as runner.json `"releaseKey"`; a new release never brings its own key) and carrying a **higher release number** than what runs now. The number is signed with the manifest (`manifest.sig` v2: `ed25519:<key> <signature> <release>`, over `relay-runner-manifest:v2\nrelease <n>\n` + manifest.txt; `kitebook release sign` / `scripts/sign-release.ts sign` number it with the signing time, always above the last one), so an older genuine release served again is refused like a tampered one. Every update (client/updater.ts): check the signature and number, download and sha256-check every file, keep the previous version, run the new `runner.ts --help` as a health check, and switch back to the previous version if it doesn't start; then the `kitebook` command (`~/.local/bin/kitebook`) and the agents' Kitebook entries (Cursor, Gemini CLI, opencode JSON) are brought in line, and the runner restarts by itself once its tasks finish. History: `~/.kitebook/updates.json` (Settings shows it) and the audit log.
- **Settings -> Updates** (per Mac): the release it runs vs the newest one, **Update now**, and **Install signed updates automatically**, which is **on by default** (runner.json `"autoUpdate": false` turns it off; the Mac checks every 6 hours and installs only when idle). An install with no release key pinned, or a signed release without a number, is never installed on its own: it waits for one click on Update now (an owner-signed change, like every Mac setting in Settings).
- **Agents**: `relay_update` (MCP tool / `POST /v1/relay_update`) takes **no arguments** (a version, link or code is refused), needs an app that can write, and is answered from the Mac's last check: `will_install`, `refused` with the reason (already newest, bad signature, another key, older release), or `needs_owner` (no key pinned: Settings shows who asked, one click approves). The answer's top level is the Mac's `{state, from, to, why}`. On a **git install** (the one-step install) an app's ask **installs the latest right away, with no confirmation** (owner, 2026-10-22 22:00: "update is fine, just remove those barriers except it could only pull from latest"). Any of the owner's own connected apps that may send tasks in the workspace (assistants like Hark or Claude.ai, or an agent with dispatch) can ask; the ask is handled by the **runner process itself** (never a task, never Pi or another coding agent): it fetches origin into private refs and, once its running tasks finish, fast-forwards to the **newest commit of the branch the checkout follows** (with Experimental on, origin/dev, else origin/main; with Experimental off, its upstream: origin/main for a normal install, origin/dev for a checkout you set to follow dev; any other upstream is refused). The commit is resolved again right before the move, so it is always the latest then. The app can't pick anything: no sha, branch, link or older version (arguments are refused), never a downgrade, never a rewritten history; a dirty tree, a local commit or a changed origin are refused too. The move is the same update as Settings -> "Update to dev now" (pinned to that sha for the one update; the new runner must load, server health check, roll back on failure), then a self-check (load + reach the server) and an idle restart, watched like a git pull. The app answers `updating`; asking again reports the same ask, then its outcome once (`updated` with the sha and health ok, `rolled_back` / `refused` with the reason, `up_to_date`). Settings -> Updates shows **Updated by Hark to abc1234** and the audit log has each one (`update_dev`, approved_by app). No confirm code, presence prompt, Experimental or standing switch is involved. **The owner's kill switch:** Settings -> Updates -> **Let apps update Kitebook** (on by default, per workspace): off, `relay_update` answers `needs_owner` and the Mac is handed no asks; turning it back on needs presence (`kitebook confirm`). The old "Install updates without asking me" switch and the `kitebook confirm` step for updates are gone; a Mac upgrading from them drops its saved standing approval and treats an ask still waiting for a code as an app's ask (it updates to the latest). A runner still on an older Kitebook (374169f) doesn't report `update.nogate`, so the server keeps its old flow for that Mac: `waiting_approval` until the owner confirms there. Each ask shows in Settings -> Updates (who asked, from -> to, result) and the audit log (`update_dev`, `update`). Inside a task, `kitebook-svc update` installs a signed newer release the same way. Every ask is shown in Settings.
- `kitebook update` in a terminal does the same with no prompt. The only terminal y/N left is for a **git checkout** moving to an arbitrary commit (below). `"releaseUrl"` in runner.json (owner-only) fetches releases from a mirror; the signature decides, not the address.

**Errors say what to do.** With no `approve` set the runner uses the Mac dialog (plus phone when `ntfy` is set), phone elsewhere, and the terminal only when it really has one. When nobody could be asked (e.g. `approve: terminal` under launchd), tasks are rejected with the exact `set ... approve ...` command instead of a silent "declined". A missing agent CLI rejects the task before asking you, with the install command. At startup a bad token, wrong URL or unreachable Kitebook prints one line with the fix (unreachable retries with backoff; under launchd a fatal error waits 5 minutes before exiting, an hour for a rejected token, so the log isn't flooded). A runner revoked while it runs (Status -> Revoke, admin revoke/rotate) stops at once instead of reconnecting: it prints the reinstall line (`<kitebook>/start` -> Connect your Mac, `KITEBOOK_FORCE=1`) and `runner.ts uninstall <cfg> --purge`, and exits 3. An installed runner checks its own files against the version's manifest at start and refuses to run a changed one, with the reinstall line. `runner.ts help` lists the commands; `set <cfg> ntfy.server <url>` points phone approvals at a self-hosted ntfy. A first install whose claim fails (used or expired invite) removes the read-only files it had just put down, and a hostname like `(none)` becomes the name `mac`. `doctor` prints `ok` / `FIX ... -> <command>` per check and exits 1 if anything needs fixing. Token and invite fixes point to `<kitebook>/start` (**Connect your Mac** for a new install line, run with `KITEBOOK_FORCE=1` to replace the config; **Status -> Revoke** to cut a client off), so hosted users never need a repo clone.

**A broken approval channel is never a "no".** When every way to ask you fails (the ntfy server is down or refuses the push, the review page can't be served with a passkey on), nobody was asked, so the task isn't rejected. A runner that asks on the phone keeps the task in `awaiting_approval` instead and opens the owner-only review page, so you can still Approve/Reject it from the /start Status card (Needs you shows **approvals down: <cause>**); it keeps retrying the push meanwhile (30 s, doubling, capped at 10 min) and whichever answer comes first counts. Otherwise (or if that page can't be served either) the runner hands it back to `queued` (`task_release`) with the note `approval channel unreachable: <cause>; run doctor on <runner> ...` and asks again with backoff (30 s, doubling, capped at 10 min). Meanwhile its advertised capabilities carry `approval: {ok: false, error, since}`, `peers` shows `approval_unreachable` on that runner, and the /start Status card marks it **approvals down**. The flag clears on the next successful push. `doctor` really probes the ntfy server (`/v1/health`), so it no longer says `ok` while the phone channel is dead. Only a real answer rejects: **declined by the user**, or **no answer within 15 minutes** when you were asked but didn't respond.

## Keep it always on, approve from your phone
- `bun client/runner.ts install runner.json` (macOS) registers a launchd agent. It starts at login, restarts if it dies, and reconnects after sleep. Tasks sent while the Mac was off wait in its inbox. Add `"keepAwake": true` to stop the Mac sleeping while plugged in. `uninstall` removes it; `uninstall runner.json --purge` also revokes the runner's token on the server (`revoke_self`) and deletes `~/.kitebook`, `~/.kitebook-kb` (the KB read cache, i.e. your notes as text) and the log, so nothing usable is left on the Mac (a `kb.cache` set elsewhere is named so you can delete it). If the server can't be reached it says to revoke from /start -> Status -> Revoke. Logs go to `~/Library/Logs/kitebook-runner.log`.
- **Runner health and self-heal** (incident 2026-10-23: the runner went offline while the server stayed up, and tasks queued silently for hours). Any connected app can call op `status`: a plain-words verdict ("Working", "Runner stopped 2h ago", "Mac unreachable, last seen 3h ago"), the next step for the owner, each runner's last_seen, running/queued tasks and last exit reason (the runner writes `~/.kitebook/runner-exit.json` on a crash, a signal or a restart), queued tasks that can't run as asked ("codex isn't installed on mac"), and relay_update asks still waiting; `kitebook status` prints the same verdict as its `health` line. task_create checks the same before queueing (a missing agent, model, project or checkout on an online runner is refused with the reason; to an offline one it queues and says how long the runner has been gone), and the runner re-checks when it claims. On macOS a second launchd job, `dev.kitebook.watchdog` (`client/watchdog.ts`, once a minute; installed with the runner job, or by the runner itself at start on a Mac set up before it), restarts a runner the server has lost for over 2 minutes while the server answers (`kickstart -k`, or loads the job if it was unloaded), at most 3 times an hour and 2 minutes apart, never one you stopped with `kitebook stop runner`; after 10 minutes down it sends one push to your phone (the ntfy topic approvals use) and /start shows a banner. Logs: `~/Library/Logs/kitebook-watchdog.log`; each restart and alert is in the audit log. `"watchdog": {"off": true}` in runner.json turns it off. The runner also drops and reopens a socket that never opens (30 s) or stops answering pings (95 s), so it never stays alive but disconnected.
- **The `kitebook` command** (install.sh puts it at `~/.local/bin/kitebook`, no sudo; `KITEBOOK_BIN_DIR` moves it; a git install's runner writes it at start-up when it's missing, and adds `~/.local/bin` to your shell's PATH in a marked block when a new login shell wouldn't find it: client/cli-path.ts) manages Kitebook's own server and runner, in plain words, so you never type `launchctl`: `kitebook status` (server and runner up/down, version), `kitebook restart [server|runner|all]`, `kitebook stop|start [server|runner|all]` (stop keeps it stopped until start, even across KeepAlive), `kitebook logs [server|runner] [-n 60] [-f]`, `kitebook update` and `kitebook pin <sha|version>` (below), `kitebook doctor`. On a Mac that hosts Kitebook with no server or domain, the same verbs take `tunnel` (`kitebook restart tunnel` gets a new cloudflared, `kitebook logs tunnel`), and `kitebook tunnel` shows the public address and its health ([storage](storage.md#self-host-on-an-always-on-mac-no-server-or-domain-needed)). On macOS it drives the launchd jobs; on Linux the `kitebook-runner` / `kitebook-server` systemd user units (`"runnerUnit"`, `"server": {"unit"}` rename them); with neither it says so. It reads `~/.kitebook/runner.json` (`--config` or `KITEBOOK_RUNNER_CONFIG` for another), and every kitebook op (`kitebook task_create ...`) still works through the same command. Agents get the JSON form as `kitebook-svc status | restart | update`; stop/start/logs/pin are owner-only.
- Under the hood that is `bun client/runner.ts service runner.json status | restart server|runner|all | update | pin <sha|version>`, which manages Kitebook's own launchd jobs. For a **pinned install**, `update` installs the newest signed release with no prompt (see Safe updates); a release that isn't signed with a number waits for Update now in Settings (or `pin <version>`, stored as `runnerPin`). Every file is checked against the server's manifest before `current` switches, a mismatch is refused, the previous version is kept for rollback, and the runner restarts once it's idle. **A push to main no longer updates your Mac by itself** (that push would be code execution on it); a `git pull` you (or your coding agent) run in the checkout does: the runner (client/git-pull.ts) fetches origin itself and applies only a fast-forward to a commit on origin's main or dev with a clean tree, after the new code's `runner.ts selfcheck` passes (else it rolls the checkout back), restarting once idle; deps install when the lockfile changed, a server still on cf dev is upgraded, and three starts that never reach the server roll back to the previous commit (`"gitWatch": false` turns it off). `kitebook update` itself: `update` fetches, then fast-forwards *only* to a commit you approved, either `updatePin` in runner.json (`service runner.json pin <sha>`, owner terminal only, refused from inside a task; `pin -` clears it) or, from your own terminal, a y/N prompt listing the incoming commits. Without either it's refused with the incoming list, and history that isn't a fast-forward is never applied, even when pinned. Then it copies code into `server.dir` without creating backup folders (Git supplies the previous code for rollback), restarts the server, health-checks it, rolls back if it fails, then restarts the runner once it's idle. Agents get the same tool as `kitebook-svc`. It only touches `dev.kitebook.server`/`dev.kitebook.runner`, and raw `launchctl` stays blocked. Set `"server": {"dir": "/Users/you/relay-cf"}` in runner.json when the server runs from a separate folder.
- Switch anytime: `bun client/runner.ts set runner.json approve phone` (or `dialog`, `dialog+phone`, `terminal`, `browser` (/start Status + `kitebook approve`, the default `init` writes off macOS); unset = dialog on macOS, see First run; with nothing set and no dialog, terminal or phone on the machine, tasks wait on the review page and `kitebook approve` and doctor warns, rather than being refused). A running runner picks it up within seconds, and the first switch to phone generates your private ntfy topic.
- `"approve": "phone"` or `"dialog+phone"` sends each approval to your phone through [ntfy](https://ntfy.sh) (free app on Android/iOS, or self-host the server) with **Approve / Reject** buttons, and the first answer wins.
  - Setup: set `"ntfy": {"topic": "kitebook-<long random>"}`, then subscribe to that topic in the app.
  - The runner stays outbound-only. Each ask carries a one-time nonce, so a forged or replayed reply is ignored.
  - Treat the topic name like a password, or use ntfy access tokens (`"token"`).
  - The push is also asked for before a `git push` when `"push": "ask"`.
- **From the `/start` Status card** (any device, signed in as the owner): Needs you lists each waiting approval with a link to its review page and Approve/Reject buttons, each open question with an Answer box (it goes through the same path as `task_answer`, recorded as `answered_by: owner`), and every open task has Cancel. On the dialog-only path the runner opens the review page too, marked owner-only: the server serves and decides it only for the account owner's session (no session -> a sign-in link back to it). With `approvePasskey` the card only rejects; Approve opens the review page, where your passkey signs the nonce and the runner verifies it. Card actions need the session cookie, a same-origin JSON POST and a one-time nonce (`op: nonce`, 5 minutes, single use). A dialog-only runner advertises `approve_ways` and `phone_on` (the exact `set <runner.json> approve dialog+phone` command), and the card offers it.
- **Every approval is bound to the exact payload** (`client/approval.ts`). The runner hashes what will run (instructions, title, acceptance, scope, project, agent, model, verify, access, continue_from, spec) and the ask's nonce is `HMAC(runner-only key, task id | hash | expiry)`, valid **5 minutes**. Each prompt (dialog, terminal, ntfy, review page) shows the first 8 hex chars of the hash as an *approval code*. When you answer, the runner re-fetches the task and re-checks: if anything changed since the ask (even the owner's own `access` switch), or the answer came after the expiry, the approval is void and you're asked again with a new code. An unanswered ask is re-sent after 5 minutes, up to 15 minutes in total. Run, push and irreversible-action approvals use separate gates, so one can't be replayed as another.
- **Signed dispatch (needed for `approve: auto`).** With `approve: auto` the runner used to trust the sender *name* the server reports, so a compromised Kitebook, a leaked `ADMIN_TOKEN` or any token with `dispatch` could run code on the Mac. Now each dispatcher can sign its tasks end to end (`client/sign.ts`):
  1. On the dispatcher: `kitebook keygen` writes an Ed25519 key to `~/.config/kitebook/signing-key.json` (mode 600; `KITEBOOK_SIGNING_KEY` moves it) and prints the public key (`ed25519:…`). The private key never leaves that machine. **Hark:** keep the key file next to its kitebook token (same secret store, same handling), point `KITEBOOK_SIGNING_KEY` at it and dispatch with `bun client/cli.ts task_create ...`, or call `signCreate()` from `client/sign.ts` before `task_create`.
  2. On the Mac, out of band (you copy the public key yourself): `bun client/runner.ts trust add runner.json hark ed25519:…` (writes `trustedKeys` in runner.json, 0600, an owner edit that agents can't make; `trust list` / `trust remove`). Then `bun client/runner.ts set runner.json requireSignedAuto true`.
  3. `kitebook task_create` then signs automatically (`--unsigned` to skip). The signature is Ed25519 over `task id | target | from | timestamp | nonce | payload hash`, where the hash is approval-v2's canonical payload hash (`payloadOf`, gate `dispatch`, with the agent/model the sender asked for). The sender picks the task id, so the signature covers it.
  4. Before auto-running, the runner re-hashes the task as the server has it and checks: a key trusted for that sender, same id/target/sender, a timestamp within **10 minutes**, a nonce it has never seen (persisted in `~/.kitebook/nonces-<runner>.json`), and a valid signature. Then it runs exactly the task it verified. **Unsigned, tampered, stale, replayed, or signed by an unknown key: it is never auto-run.** It falls back to the human path (phone if ntfy is set, else the Mac dialog), the prompt says why ("Not auto-run: …"), and the fallback is audit-logged. `trusted` (names) still narrows who may auto-run. A promoted plan changes the payload, so it always asks you.
  5. **Chains.** A chained task (`chain: [...]`) signs its whole chain definition (goal, steps, verify) along with step 1, so the steps the server creates later inherit its trust instead of asking you each time. A child step auto-runs only if this runner verified the signed parent itself when step 1 ran, the parent's signature still matches the parent as the server has it (chain included), the child is exactly that step of the signed chain (its rendered instructions, agent, model, kind, verify, project, scope and sender), it follows up on the previous step of the same chain, and no other task already ran as that step. Anything else asks a human. Records last 14 days, so a chain that pauses longer asks again.
  - The signature also covers `kind` (it steers per-kind agent prefs) and, for follow-ups, the project/agent/model a `continue_from` inherits (a different agent doesn't inherit the old model), and git-first `repo`/`base`. Give `project` along with `repo` when signing: mapping a repo URL to a project happens on the server, so a repo-only signed task asks you. KB notes are signed too: the CLI fetches the task's top-k KB hits itself (`pickKb`), sends their ids as `kb_ids` (the server attaches exactly those) and signs the list of entry ids + content hashes; on a signed auto-run the runner keeps only `kb_context` entries whose id and hash match and drops the rest (audit `kb_unsigned_dropped`). An older signature without a list still verifies and means no KB. A signature proves who sent a note, not who wrote it, so KB provenance counts too: every KB entry records its `author` (the peer that committed its text, from its token, never from front matter) and `author_kind`; the CLI signs only notes authored by the sender itself or the target runner (its own `kb.sync` memory and learnings), plus `KITEBOOK_KB_TRUST=peer,...` / `--kb-trust`, lists the rest on stderr and signs each kept note's author with it; and on a signed auto-run the runner keeps only notes whose (signed) author is in `trustedKbAuthors` (default: the peers in `trustedKeys` plus the runner itself; when set, the list plus the runner), dropping the rest (audit `kb_untrusted_author_dropped`). Human-approved and unsigned runs still get those notes, labeled `UNTRUSTED author <peer>` in the prompt, and the approval ask lists them. So a note a Codex token or a chat assistant wrote never reaches a signed auto-run unless you trust its author. `CONTEXT.md` and the `context/<project>.md` pack aren't signed, so signed auto-runs leave them out (audit `context_unsigned_skipped`) unless you set `"trustContextFiles": true` (`bun runner.ts set runner.json trustContextFiles true`); human-approved runs get them as before.
  - Existing `approve: auto` configs without `"requireSignedAuto": true` keep working as before (an invalid signature still never auto-runs), but the runner prints a loud warning at startup. `runner.ts init` writes `"requireSignedAuto": true` into new configs. The runner advertises `signing` in its capabilities.
- **Review page.** The ntfy notification opens `<kitebook>/approve/<one-time id>`, a page the server serves with the full task (title, from, runner, project, agent/model, verify, access, full instructions, approval code) and **Approve / Reject** buttons. One decision per id, 5-minute life, JSON POST only (a link preview can't decide), strict CSP, `no-store`. Without a passkey the classic Approve/Reject notification buttons still work too.
- **Passkey (opt-in).** `bun client/runner.ts passkey register runner.json [label]` prints a one-time link (10 minutes); open it on your phone and create the passkey. Its public key is saved in `runner.json` (a protected file). Then `bun client/runner.ts set runner.json approvePasskey true`. From then on the notification only links to the review page, Approve asks for your passkey (user verification required) and signs the approval nonce, and **the runner** verifies the WebAuthn signature (ES256, EdDSA or RS256; challenge, origin, rpId, UP+UV flags), so neither ntfy nor the server can approve on their own. Direct ntfy "approve" replies are ignored; Reject still needs no passkey. `passkey list` / `passkey remove <id>`. The passkey belongs to the server's hostname (`url` in runner.json), so register again if that changes. The Mac dialog and terminal prompts are unchanged (you're at the machine).

## Zero-touch (opt-in)
**Standing permissions instead of zero-touch:** most owners want "Hark may run tasks in these projects without asking", not a machine that runs everything. Set it on `/settings` → Connected apps (or tick "Let it run tasks on its own" when the app connects, or "Always allow" on a review page). This Mac follows it only for permissions signed by a browser key in runner.json `"ownerKeys"` (`init` pins the ones on the server at install; later browsers: Settings → Devices & passkeys → Trust; or the older `bun ~/.kitebook/current/runner.ts owner runner/runner.json <fingerprint>`), in any `approve` mode, and pushes still ask unless the permission says "can push". To answer asks at the keyboard instead of the phone: `kitebook approve`. See [standing permissions](security.md#standing-permissions).

`approve: auto` + `access: full` runs signed tasks with no prompt. It's never the default, and only the owner can turn it on, on the Mac: `./scripts/zero-touch.sh [runner.json]` refuses until at least one dispatcher key is trusted (`kitebook keygen` on the dispatcher, then `runner.ts trust add`), then sets `requireSignedAuto true`, `approve auto`, `access full` and runs `doctor`. Unsigned or invalid tasks still ask you, and the [protections](security.md) stay on. Undo with `set runner.json approve dialog` and `set runner.json access worktree`.

## Leases (a runner that never comes back)
Claimed, awaiting-approval and running tasks carry a server-side lease. While the runner is connected the lease never expires. If it goes offline and stays silent past the lease (default 900s; `LEASE_SEC` var per kitebook, or `limits.lease_sec` per task), a Durable Object alarm takes it back. `needs_input` isn't leased, since it waits on the sender (however long); the lease restarts when `task_answer` puts it back to `running`.

**Automatic retry.** Infrastructure failures (the lease expired, or the runner crashed/restarted mid-task) requeue the task instead of failing it, up to `max_retries` times (`task_create`, 0-5, default 1). `task_get` shows `attempt`, `max_retries` and `attempts[]` (reason, state it was in, partial commit). The event log gets `task.retrying` then `task.queued`. The retry runs on the **same branch**, on top of whatever the interrupted attempt left (the runner commits it as `[interrupted, partial]`), and an attempt the owner already approved isn't prompted again. When retries run out the task fails with `result.reason` (`lease_expired` / `runner_crash`) and `retryable: true`; follow up with `continue_from`. A runner that comes back kills the stale agent; one that was only disconnected stops its stale attempt and picks up the new one.

**Crash-safe partial results.** The runner tees the agent's output to `~/.kitebook/logs/<task>.log` while it runs. After a crash, the restarted runner commits what the agent left in the worktree on the task branch and uploads `diff.patch`, `agent.log` and `git.json` with the failure (they stay readable at that attempt's commit even after a retry overwrites them).

## Agent presets and follow-ups
- `"agent": "pi"` in a runner project uses Pi's built-in command line (install it with `npm i -g @earendil-works/pi-coding-agent`; the old `@mariozechner/pi-coding-agent` package stopped at 0.73). No `agents` block is needed. Custom templates can use `{prompt}` and `{session}`.
- **Checked adapters** (client/agent-adapters.ts): `"codex"` (Codex), `"claude"` (Claude Code), `"gemini"` (Gemini CLI), `"cursor"` (Cursor's `cursor-agent`), `"copilot"` (GitHub Copilot CLI), `"opencode"` and `"grok"` (Grok CLI) are built in. At startup the runner reads each installed CLI's `--help` (Codex: `codex exec --help`) and builds the command only from flags that help lists, because flags drift between versions (Codex dropped `--full-auto`, and a hard-coded preset made every Codex task exit 2): a flag a run needs that's missing (e.g. an old Copilot without `--allow-all-tools`, an old Codex without `--sandbox`) means the agent isn't offered for tasks, and Settings, `doctor` and the refusal say which flag and how to update; optional flags (Codex `--skip-git-repo-check`, Gemini `--skip-trust`, Cursor `--trust`, Copilot `--no-ask-user`/`--silent`/`--no-auto-update`, Grok `--always-approve`) are added only when listed. What each one runs:

  | agent | task run (in the worktree) | live output | later turns of one task | quick asks |
  |---|---|---|---|---|
  | codex | `codex exec --sandbox workspace-write [--skip-git-repo-check] <task>` (approvals are off in exec) | `--json`: commands, messages, thread id | `codex exec ... resume <thread id> <text>` | `codex exec --sandbox read-only` (built-in preset) |

  "Later turns" are the sender's answer to a question, a steering note, and a self-repair round: with resume, only the new text goes in and the agent keeps its conversation; without it the original task is sent again. `<task uuid>` is a UUID Kitebook derives from the task id, so a restarted runner uses the same one and a later turn can only continue this task's own session. A model goes in with each CLI's `--model`/`-m` (opencode's list comes from `opencode models`; Gemini's aliases auto/pro/flash/flash-lite; Codex and Claude have known ids/aliases). Cursor, Copilot and Grok have no model list that works without a login, so an explicit model for them (a task's `model`, `prefs.defaultModel`, Settings) is passed through as given with a log line, and the CLI itself says if it doesn't know it; `"models": {"cursor": [...]}` in runner.json advertises a list (then it's checked). Quick asks run a fresh process per question under the same OS read-only sandbox; an agent whose `--help` lacks the read-only flags (and the community grok-cli, which has none) answers with the before/after git check on top, so an answer whose run changed the checkout is withheld. A runner.json `agents.<name>` entry overrides a built-in.
  - **Live connections** (client/live-driver.ts, client/live-codex.ts). Where an agent has a protocol for it, a task keeps ONE live session for all its turns instead of one CLI process per turn: a steer reaches the running turn, cancel interrupts the turn (and the process tree), and the agent's own approval asks go through Kitebook. Today that's Codex through `codex app-server` (JSON-RPC over stdio; codex 0.146 or newer with the app-server subcommand; the protocol slice is generated from codex 0.163's stable bindings): `thread/start` (or `thread/resume` of the task's own thread after a restart or a parked question), `turn/start` per turn, `turn/steer`, `turn/interrupt`; quick asks keep a warm app-server session per asker. Sandbox per turn: tasks keep Codex's own `workspaceWrite` sandbox on the worktree with approvals off (`never`), exactly like `codex exec --sandbox workspace-write`; runner.json `"codexApprovals": "on-request"` lets Codex ask to go past it, and those asks always go to you (gate `agent`, even with approve auto; a file change inside the worktree is allowed), no answer in `liveApprovalSec` (300) is a no. A thread open in another Codex is never written to (resume -> `thread/fork`). The CLI stays the fallback, invisibly: no driver, an old Codex, a failed handshake (then CLI for 30 min) or runner.json `"live": false` / `{"codex": false}` runs `codex exec` as before; a custom `agents.codex` entry always wins. `describe` -> `agents_detail[].live`, `doctor` says which one runs.
  - **Codex and nested sandboxes (macOS).** Seatbelt profiles don't nest: a Codex that applies its own sandbox inside another one dies with `sandbox-exec: sandbox_apply: Operation not permitted` before it runs anything (openai/codex#45657). Quick asks already run inside Kitebook's read-only sandbox, so Codex applies none there: the live session uses `sandboxPolicy: externalSandbox`, the `codex exec` fallback `--sandbox danger-full-access`, both only inside Kitebook's wrapper (with no OS sandbox on the computer Codex keeps its own `--sandbox read-only`). `doctor` says so, and flags a runner that itself runs inside a sandbox (then nothing can apply one under it; run it as its login service).
  - **Checked against:** each CLI's own documentation (Codex non-interactive docs; Claude Code CLI reference; Gemini CLI cli-reference + headless; Cursor CLI parameters + output-format; GitHub Copilot CLI command reference; opencode CLI docs and its `run --format json` events; xAI Grok Build headless docs; the community grok-cli's source), the **real binaries' `--help`** (codex-cli 0.163, claude 2.1.304, gemini 0.64, copilot 1.0.100, opencode 1.19.3, cursor-agent 2026.10.19, Grok Build 1.0.62, pi 1.3.0; `scripts/agents-help-check.ts`, also a CI job that installs the npm CLIs and needs no login), and in smoke against fake CLIs (`scripts/fake-agents.ts`) that print exactly those flags in `--help` and refuse any other (the fake Codex refuses `--full-auto` with exit 2 like the real one). opencode ran end to end for real (task, events, resume, read-only ask). **Not yet run with a login** (the real CLIs stopped at auth): the live event streams of Codex, Claude Code, Gemini, Cursor, Copilot and Grok (field names come from the installed bundles, official docs or the CLIs' own emitters), and two known upstream quirks: opencode's `--format json` can drop the final text event in containers (the task still succeeds; only the summary is shorter), and Gemini's yolo mode has asked for confirmation in some headless versions. Two different CLIs are called `grok` (xAI's Grok Build and the community grok-cli, recognised by "powered by Grok" in its `--help`); both take `-p`/`-m`, only Grok Build lists `--always-approve`, `--permission-mode` and sessions. Both installers also put a second `agent` binary on PATH, so Kitebook never runs a bare `agent` for Cursor.
- **Coding agents in Settings.** Settings -> **Coding agents** lists, per Mac, the agents it found and what each can do there (runs tasks, quick asks read-only or checked, keeps its conversation between turns), with one-click **Connect** (the Mac wires that agent's MCP config to Kitebook, like `kitebook connect <agent>`: its own folder, no task sending) and **Which agent works on each project** (saved on the Mac as runner.json `prefs.byProject.<project>.agent`; a task that names its own agent still wins if allowed). Both are owner commands signed in a browser the Mac trusts (`connect_agent`, `default_agent`), like every other Mac change from Settings.
- **Auto presence.** The runner reports every agent session it starts to Who's working (`presence`) with its agent, model, repo, branch and phase: task runs, parked tasks waiting for an answer, quick asks while they answer ("answering a quick question") and warm quick-ask sessions between questions ("ready for quick questions"). Agents never have to call `presence_report` for work Kitebook gave them.
- To follow up, call `task_create` with `continue_from: <finished task id>`. It goes to the same runner and project and continues on the **same branch**, so the existing PR updates. With Pi it also resumes the **same session** (one session file per branch). The other agents start a fresh session with a note that earlier work is already committed. The new task's `git.json` records `continues`.
- **Cross-agent handoff.** A follow-up may switch agent, model or kind (`continue_from` + `agent: "claude", kind: "review"`: Codex wrote it, Claude reviews it). The model is only inherited when the agent stays the same. The runner writes a handoff note into the new agent's prompt from the previous task's structured result and its diff stat: what was done, files changed, test status, risk flags, open questions (an "Open questions:" list or `?` lines in the previous summary) and the previous agent's closing notes. It's saved as `tasks/<id>/handoff.md`. Agents are asked to end with "Open questions:" so the next one gets them.
- **Chains.** `task_create` with `chain: [{agent, model?, kind: "code"|"review"|"test", instructions, verify?, title?}, ...]` (1-8 steps) runs the steps one after another on **one branch**. `instructions` is the overall goal every step sees, with the plan and its own step. The created task is step 1 and the chain's parent; each later step is a child task (`parent_id`, `chain_step`, `continue_from` = the previous step, so it gets the handoff note), created only when the previous step **succeeds**. A failed, rejected or cancelled step stops the chain. `task_get` on any step shows `chain: {parent, steps: [{step, kind, agent, task, state}], status: running|succeeded|stopped, stopped_at}` and the parent lists `children`. Each step is its own task, but you approve an unsigned chain once: the step 1 prompt says it approves the whole chain, and the approval is bound to the chain definition's hash (goal, every step's kind/instructions/agent/model/verify/title, plus project, scope, title, sender). Later steps then run without asking only if the parent as the server has it now still hashes the same, the step is exactly that step of it (same rendered instructions, agent, model, kind, verify, project, scope, sender), it follows the previous step, and no other task already ran as that step; anything else asks again, prefixed "Asking again: <why>" (audit: `chain_approved`, `chain_step_approved`). Signed chains keep their signature-based trust (above); under `approve: auto` without `requireSignedAuto` steps just run. An automatic retry (lease/crash) of a step that then succeeds carries the chain on.

## Context packs
- **Per-project context** goes into every agent prompt for that project: `CONTEXT.md` in the repo (from the task's branch) and `context/<project>.md` in the space. The runner gets the space file with `task_claim` (only for the project it was sent; no `context/**` grant needed). The pack is capped (`contextMaxChars` in runner.json, default 12000; the server hands over at most the newest 64k chars) and content-hashed: an agent that resumes its session (`{session}` in its argv, like Pi) gets "context <hash> unchanged" instead of the same text again; agents without a session get it every time. `result.structured.context = {hash, sent}`.
- **Learnings.** The agent is told it may write durable notes (build quirks, conventions, gotchas) to `.relay-learnings.md` in its worktree. The runner reads and removes it (it's never committed) and sends it with `task_complete`; after a **successful** task the server appends it to `context/<project>.md` under `## Learned in <task> (<agent>, <date>)`. It's secret-guarded like any write: a note that looks like a key is refused (`result.learnings.status: "refused"`) and the task still succeeds. Edit or trim the file whenever you like; it's an ordinary space file.

## Parallel runs, agent/model per task, cancel
- **Parallel.** The runner runs up to `maxParallel` agents at once (default 3), never two on the same project checkout. Claiming, checks and approval happen outside those slots, so a task waiting for your OK never holds up other work; a task that is approved but has no free slot reports "waiting for a free slot".
- **Pick the agent and model.** `task_create` takes `agent` and `model`. At startup the runner fills each agent's model list by asking its CLI non-interactively (`pi --list-models`; Claude Code gets its documented aliases `sonnet`/`opus`/`haiku`, Codex a known-models fallback list; add your own with runner.json `"models": {"codex": [...]}`). It advertises them as `models` in `shared/runners/<name>.json`. A bad agent or model is refused, both by the server at `task_create` and by the runner, with the advertised list. The model goes through each preset's model flag (`pi --model`, `codex -m`, `claude --model`). Custom agents: `{"argv": [...], "listModels": [...] | "models": [...], "modelFlag": "-m"}` or a `{model}` placeholder; the agent also gets `KITEBOOK_MODEL`.
- **Owner preferences bound the pick.** runner.json `"prefs": {"defaultAgent", "defaultModel", "byKind": {"plan|code|review|test|quick": {"agent", "model"}}, "byProject": {"<name>": {"agent", "model"}}, "allow": ["codex/*", "claude"], "deny": ["claude/opus*"], "askWhenUnsure": true}`. The runner resolves each task as: the dispatcher's explicit `agent`/`model` (if allowed), then `byProject`, then `byKind` (task field `kind`), then the defaults; a disallowed choice is refused with the allowed list. The choice and why (`agent_reason`: task/project/kind/default) land in `result.structured`. Prefs are advertised in `shared/runners/<name>.json` and in `peers` (`capabilities.prefs`), so assistants read them before dispatching and only ask you when `askWhenUnsure` is on and nothing fits. Set them on the Mac: `bun client/runner.ts set runner.json prefs.byKind.review.agent claude`, `prefs.byProject.myapp.model gpt-5.5`, `prefs.allow "codex/*,claude"`, `prefs.askWhenUnsure true` (`-` removes a key); a running runner picks them up within seconds.
- **Ready-to-run worktrees.** After `git worktree add`, gitignored dependency dirs in the main checkout (`node_modules`, `.venv`, `vendor`, `Pods`, `target`) are cloned copy-on-write (`cp -c -R` on macOS/APFS, `cp --reflink=auto -R` on Linux), falling back to a symlink. They're never committed. With no `verify`, the runner detects the repo's own test command (package.json `test` script, `bun test`, `cargo test`, `pytest`), runs it and reports it. Finding none is fine; a failing auto-detected test marks the result `partial` with a `tests_failed` risk flag but doesn't fail a task nobody asked to verify.
- **Live session status.** While a task runs, the runner reports its phase (`waiting_approval` → `approved` → `agent_running` → `verifying` → `uploading` → `done`; `queued`/`done` come from the task state), agent, model, Pi session file name, `started_at`/`elapsed_s` and the last output line. Read it with `task_status` (one task by `id`, or all your open tasks; also an MCP tool), in `task_get` as `live`, and in `peers` as each runner's `active_tasks` (title and last line only for tasks you sent or received). The agent's output tail streams into `tasks/<id>/live.log` (every `liveEvery` seconds, default 10, capped at 64KB). Everything is redacted on the server like other reports. When the installed `pi` supports `--mode json` (checked at startup with `pi --help`), the pi preset runs in JSON event mode so the live log shows tool calls and retries; the final answer is pulled out of the events, so summaries look the same. Older pi: plain `-p` lines.
- **Result headline.** Every finished task gets one fixed, phone-first card, `result.headline` (and first in `task_get`, the `kitebook://task/<id>` resource as `result_headline`, the Status card's Recent rows, `inbox` finished and `task.completed` pushes as text): outcome (done, failed, needs you, stopped), what changed (files, +/- lines, test files), which test command ran and whether it passed, the branch, how long the agent worked, and ONE next action (the merge command or PR link, retry as a follow-up, reply, push, or run the plan). The runner builds it; for a task no runner finished (rejected, cancelled early, an assistant target) the server builds the same card. Status also shows a week line: tasks done, agent wall time, and task branches the runner saw merged into the default branch (squash merges aren't seen, so it undercounts). Only measured numbers, no estimated time saved.
- **Structured results.** `task_get` returns `result.structured` and `check` updates carry it as `result`: `{status: succeeded|partial|failed|cancelled, headline (<=280 chars), tests {passed, failed, cmd}, files_changed, branch, base, commit, diff_stat, pushed, compare_url, pr_url, risk_flags, duration_s}`. `result.summary` and the files under `tasks/<id>/` stay as before. Risk flags include `protected_paths:…` (AGENTS.md, CLAUDE.md, .github/workflows, package.json…), `dependencies_changed`, `files_deleted:N`, `large_diff`, `out_of_scope`, `verify_failed`/`tests_failed`, `agent_exit_N`, `timed_out`, `push_failed`, `access_full`.
- **Cancel** (`task_cancel`, `cancel_all`, CLI `kitebook cancel <id>` or `kitebook cancel --all [--peer p] [--target t]`, MCP tools of the same names). The state becomes `cancelled` at once, with `result.reason` and `result.cancelled_by`. Queued: dropped (a runner that reconnects late never starts it). Awaiting approval: the phone/dialog prompt is withdrawn. Running: the agent's whole process tree gets SIGTERM, then SIGKILL after 5s; the worktree and branch are kept (partial work committed as `kitebook <id> [cancelled, partial]`, branch marked via `git config branch.<branch>.relay-cancelled`, a `.relay-cancelled` file in the worktree), and the partial `diff.patch`, `agent.log` and `git.json` are uploaded. The runner also re-checks the tasks it holds on every reconnect and every 15s, so a cancel it missed while offline still lands. `cancel_all` covers open tasks you sent or received.
- **Task spec v2** (optional; plain `instructions` keep working). `task_create` takes `spec: {goal, acceptance: ["cmd", ...], scope: ["glob"], forbidden: ["glob"], budget: {minutes, max_files_changed}, mode: "plan"|"execute"}` (`instructions` may be left out when `goal` is given). A spec the runner can't keep is refused with the reason: the server checks the runner's advertisement at create (runner without spec support, unknown project, an acceptance command not in the project's `verify` list), the runner re-checks on claim (e.g. `acceptance tool "cargo" … is not installed`). After the run, every acceptance command runs in the worktree and must pass; scope, `forbidden` and `max_files_changed` are checked against what changed. Any miss fails the task with `result.structured.violations` (`[{rule: scope|forbidden|max_files_changed|budget_minutes, …}]`) listed in the summary; the branch keeps the work. `result.structured` keeps every field above and adds `mode`, `acceptance` (`[{cmd, exit, passed, tests?}]` or null) and `violations`. `budget.minutes` is the run's time limit.
- **Plan, then promote.** `spec.mode: "plan"` runs the agent with a plan-only prompt: the plan is saved as `tasks/<id>/plan.md` (the agent's answer, or a `PLAN.md` it wrote), any file changes are discarded (`plan_changes_discarded:N`), nothing is committed or pushed. `task_promote {id, note?}` (the dispatcher) turns that plan into an execute run on the **same task id and branch** `kitebook/<id>`: it goes back to `queued`, the runner asks for approval again and puts the plan in the prompt. The plan run's result stays at `result.plan`.
- **`describe`**: one read for dispatchers. Each runner with `online`/`last_seen`/`wake`, `hours` (runner.json `"hours"`, free-form, advertised as-is), agents, models, projects with their verify commands (= the allowed acceptance commands), `max_parallel`, prefs, protect/paused and spec support; other peers' presence; and the task spec schema.
- **Who's working (presence).** The runner sends a heartbeat (`presence_report`) every `presenceEvery` seconds (default 30) and right away when a task starts, parks or ends: one session per task it holds (the server fills in phase, agent, project and start time from the task's live status) or one idle session. `presence` (MCP tool, CLI `kitebook presence`, the "Who's working" panel on /start, refreshed every 5 s) reads it back as plain lines like "Pi on relay-cf · branch kitebook/t_ab12 · running tests · 2m"; a session that misses a heartbeat (2 x its interval) reads offline. Coding agents can report their own sessions with `presence_report {sessions, every, merge: true}`.
- **Live steering (`task_steer`).** The task's sender (or the owner, from the Status card's text box + Send) can send a short note to a running task. It is pushed to the runner at once (logged: "steer #1 for <task> ... the agent gets it when its current turn ends") and given to the agent at the next turn boundary. Every agent CLI runs one headless process per turn and can't take input mid-run, so that is **after the agent's current run finishes** (and only if it succeeded; an agent on a live connection, Codex via app-server, gets it in the running turn instead: `turn/steer`, logged "given to the agent mid-turn", same approval rules): the runner takes the notes (`task_steer_take`, which marks them delivered) and runs one more turn with them, before verify and the report: in the same conversation for agents that resume (Pi, Codex, Claude Code, Gemini, Cursor, Copilot, opencode, Grok Build; `describe` -> `agents_detail.resumes`), else with the original task again; a note that arrives before the agent starts comes with its first turn. A question the agent asks wins: pending notes come with the answer's turn. Like an answer, a steer is text from the sender, not part of what was approved, so the prompt frames it as a request. On a task the owner approved by hand (or a signed auto-run), a steer is new instructions after that approval, so the runner first asks the owner again with the note shown (gate `steer`: `task_steer_take {peek}` lists it, `{only}` takes the approved ones, `{refused}` marks the rest, which the agent never sees). Notes the owner wrote on /start, and tasks that ran under Run tasks without asking or a standing permission, deliver without asking. Notes are kept on the task (`task_get.steers[]` with `delivered_at`, `thread.md`, the timeline on /start) and in the runner's audit log. The agent itself, other apps, finished tasks and tasks waiting on a question can't be steered.
- **Questions mid-task (`needs_input`).** An agent that can't go on without the sender ends its turn with one line `[relay-question: <question>]` (the prompt tells it how; a marker line rather than a file, since `.kitebook*` files are protected and every agent CLI already returns stdout). The runner parks the task: state `needs_input`, the question on `task_get.question` (all rounds in `questions[]`, also `tasks/<id>/progress.md`), in `task_list`, in `check` (`updates[].question` and a `needs_answer` list) and in the `task.updated` event payload (`question`). It also sends an FYI to the owner's ntfy topic if one is set. Parked tasks aren't leased, don't hold a run slot, and survive a runner restart (a local marker in `~/.kitebook/parked/`). The sender answers with `task_answer {id, answer}` (HTTP, MCP, CLI `kitebook task_answer --id <id> --answer ...`; a `task_message` from the sender on a parked task counts as the answer). The task goes back to `running` and the runner resumes the same worktree, branch and session file (Pi continues its session; agents without `{session}` get the original prompt plus the Q&A). An answer given while the runner is offline resumes when it reconnects. Cancelling a parked task drops it and keeps the worktree. `result.structured.questions_asked` counts the rounds.
- **Self-repair.** When an explicit `verify` fails, the runner gives the agent up to 2 automatic repair rounds in the same session (the failing command's output in the prompt) before the task fails. Set runner.json `"repairRounds"` (or per project, or `limits.repair_rounds` per task; 0 turns it off, max 5). Auto-detected test commands are never repaired (they only inform). `result.structured.repair_rounds` and `verify.log` (every attempt) show what happened.
- Under `approve: "auto"` with a `trusted` list, tasks from other peers now ask on your phone when `ntfy` is set (a headless Mac's dialog goes unseen), else the Mac dialog.

## Local CI (Experimental)

With **Experimental** and **Test every push** on (Settings -> More -> Experimental), the runner tests projects like CI would, on your machine, with no GitHub Actions minutes:

- **What runs:** the commit's own `kitebook.json` `{"ci": "<cmd>"}`, else its package.json `test` script (`bun run test` / `pnpm test` / `yarn test` / `npm test` by lockfile). Neither: skipped, silently.
- **When:** a new commit on a watched branch (runner.json project `"ciBranches": ["dev"]`; default the project's `dev` branch on origin, else origin's default branch; checked with a fetch every `"ciPollMs"`, 2 minutes), a task branch when its task ends, and **Run tests** (task page) or `ci_run {project, branch?}` from an assistant. The first commit seen on a branch is remembered, not run.
- **How:** a throwaway `git worktree add --detach` of that commit (the project's `node_modules` linked in), `nice -n 10`, a timeout (`"ciTimeoutMin"`, 20), one run per machine; a newer commit on the same branch cancels the queued or running older one. Only branches of the project's own `origin` (or the runner's own task branches): pull-request refs, forks and other remotes are never run.
- **Results:** passed / failed counts, seconds and the last 20 lines on the task page, in Settings -> Experimental and via `ci_status`; an audit line (`ci_run`) per run; a GitHub commit status (`kitebook/tests`) only with **Show test results on GitHub** on and a token already on this Mac.

## Zero-config projects
The runner discovers git repos (1-2 levels deep) under `roots` (`init` writes `~/code ~/src ~/projects ~/dev` or your `--roots`; configs with no `roots` use ~/Desktop, ~/code, ~/Developer) and names them by folder; explicit `projects` win. It advertises projects, agents and access at `shared/runners/<name>.json` in the space. `bun client/runner.ts discover runner.json` lists what it found.
