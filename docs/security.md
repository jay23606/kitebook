# Security model and runner protections

- Scoped tokens, stored hashed. Each peer gets verbs plus path globs per space. Invites are single-use and expire. OAuth access tokens are short-lived, refresh tokens rotate with replay detection, and the approval pages (device, consent) take JSON only, can't be framed, and need the owner (the `/start` session, a remembered browser, or a request the owner approved on their Mac; the recovery code only as a fallback).
- OAuth client registration is open by default only for public clients (no secret, PKCE required) with loopback or https redirects, and for Claude.ai / ChatGPT (with a secret, every redirect on claude.ai, claude.com, chatgpt.com or chat.openai.com): registering grants nothing, only the owner's consent does. The consent page marks a self-registered app as "unverified name" (names are cleaned of control and bidi characters, 60 chars max) and starts it on one folder with sending tasks off. Confidential clients and app schemes need `OAUTH_DCR=1` or the owner; `OAUTH_DCR=0` closes registration (the owner connects CLIs from `/start`). Registrations are rate limited per IP, and clients never approved are swept after a day. Refusals point to `/start`, never to the old master key, so no agent is taught to ask for it.
- Secret guard: `.env`, keys and private keys are refused, and so is content that looks like API keys or tokens.
- `if_match` gives optimistic concurrency, so nobody silently overwrites anyone.
- Coding work only runs on a runner, after a human approves locally. Only the runner can record that approval. Verify commands must be allowlisted on the runner.
- `approve: auto` is only as strong as the server unless you turn on `requireSignedAuto`: then auto-run needs an Ed25519 signature from a dispatcher key the owner registered on the runner, so neither the server nor a stolen token can start code on the machine (see Signed dispatch). `kitebook-svc update` installs only a newer signed release, and only fast-forwards a git checkout to a commit the owner approved.
- Standing permissions (/settings → Connected apps, the consent page, the review page's "Always allow"): an owner-signed policy lets one app run tasks on its own in named projects, optionally until a date, and never widens anything else; see [Standing permissions](#standing-permissions).
- The server never executes code, never stores agent credentials, and opens no ports on your machine.
- The runner adds owner-only protections on top (kill switch, destructive-command and deploy/spend/send tripwires, hash-chained audit log, protected instruction/CI files); see Protections.

## Protections (runner safety layer)
New runners start safe (`"access": "worktree"`, approval by dialog or phone, push never, `requireSignedAuto`), and the protections below sit under every mode, including a machine the owner opted into `"access": "full"` + `"approve": "auto"` (see [zero-touch](runner.md#zero-touch-opt-in)). They are **on by default**, cost nothing on the happy path, and only the machine owner can switch one off: in `runner.json` under `"protect": {...}` or with `bun client/runner.ts set runner.json protect.<name> on|off`. A running runner hot-reloads them like `approve`/`access`; turning one **off** waits until no agent is running, turning one on applies at once. Dispatchers can never change them (no op touches them), and the runner advertises the live state in `shared/runners/<name>.json` (`protect`, `paused`, `server_paused`). Code: `client/guard.ts`.

| Name | Default | What it stops | How to toggle |

| `destructiveGuard` | on | `sudo`, `rm -r` outside the task dir (tmp scratch is fine, other tasks' worktrees aren't), `git push --force`/`+refspec`/`--mirror`/`--all`, push to `main`/`master`, `git reset --hard` and `git clean -f` outside the task worktree, `launchctl`, `diskutil`, `shutdown`, `reboot`, `halt`, `dd`. Blocked call exits 1 with a note, and is logged. | `set runner.json protect.destructiveGuard off` |
| `irreversibleGate` | on | `wrangler deploy/publish`, `cf deploy`, `npm/pnpm/yarn publish`, `gh release create`, `gh pr merge`, `vercel` deploys, `netlify deploy`, `mail`/`mailx`/`sendmail`, `curl` POST/PUT/PATCH/DELETE to payment and messaging APIs (Stripe, PayPal, Square, Twilio, SendGrid...), also through `npx`. Allowed only when the task text asks with `[needs-owner-approval: why]` **and** the owner approves it on the phone (ntfy / review page, passkey if `approvePasskey`; macOS dialog if no ntfy), bound to the task's payload hash like every approval. **Safe updates**: an agent (or the owner, or the automatic update, on by default) can move the Mac only to the newest release signed with the key the Mac pinned and numbered higher than what runs, with no approval, because it can't choose the code: `relay_update` takes no arguments, a tampered, wrongly signed, unsigned or older release is refused, and a release that doesn't start is rolled back. Anything unsigned waits for the owner's one click in Settings -> Updates; the terminal y/N remains only for a git checkout moving to an arbitrary commit. On a git install an app's ask (one of the owner's own apps that may send tasks) moves the Mac right away, with no approval, but only to the latest: the newest commit of the branch the checkout follows (origin/dev with Experimental on), resolved by the runner itself, a fast-forward only (never back, never a rewritten history), health-checked and rolled back on failure. The trade-off (owner's choice, 2026-10-22): whoever can push to that branch can update the Mac; Settings -> Updates -> **Let apps update Kitebook** (on by default) is the owner's kill switch (off: `needs_owner`, and the server hands the Mac no asks). See [safe updates](runner.md#safe-updates).

**Signed runner releases** (today: not yet on by default). The repo ships no release key (`client/release-key.ts` is empty), so until the owner creates one on their Mac (`kitebook release-key create`, then `kitebook release sign`; see [signed releases](runner.md#signed-releases)) every install runs in legacy trust: the runner files are checked against the sha256 manifest, but the manifest itself is trusted because the server served it, `install.sh` prints a WARNING: UNSIGNED INSTALL line, and nothing updates by itself. With a release key pinned (`client/release-key.ts` or runner.json `"releaseKey"`), install, init and `kitebook-svc update` refuse a runner manifest the key didn't sign, so a compromised Kitebook can't push new runner code to an installed Mac; see [signed releases](runner.md#signed-releases). The first install trusts the `install.sh` it ran.

`bun client/runner.ts protect runner.json` shows the state. **The shims are a tripwire, not a sandbox**: they are scripts placed first in the agent's `PATH`, so an agent calling `/bin/rm` by absolute path, rewriting `PATH`, or deleting files from Python gets past them. They catch the common confused-agent mistakes and record them; a real sandbox (sandbox-exec/bubblewrap) is still on the backlog.

## Standing permissions

Approving every task on the phone is friction, so the owner can grant trust once per app and project. Code: `client/payload.ts` (what is signed), `client/policy.ts` (runner), `src/policy.ts` (kitebook), `src/policy-ui.ts` (browser).

- **What is stored:** one policy per workspace, `{v: 1, type: "relay-policy", space, seq, at, apps: {<app>: {tasks: "ask" | "auto" | "off", projects: [...], push, until, keys: ["ed25519:..."]}}}`, plus an audit list (one line per change, what Undo restores). Folder access stays the server's normal per-app access (verbs + folders); "can't send tasks" removes the send-tasks permission there too.
- **Who signs it:** the owner's browser. `/start` makes a P-256 key with WebCrypto (not extractable, kept in IndexedDB) and registers only its public half; every change is signed over the canonical JSON (`relay-policy:v1|<canon(policy)>`). The server accepts a version only if a registered owner key signed it, it is for that workspace and its `seq` is exactly one more than the current one (so two tabs can't overwrite each other) and only one app changed; writes also need the `/start` session and a one-time nonce.
- **Who enforces it:** the runner, locally. It reads the policy from the server (runner op `policy`) before each task and uses it only if a key in runner.json `ownerKeys` signed it (`init` pins the keys the server lists at install, the same trust as the `install.sh` it ran; later browsers trust themselves with `kitebook open`'s one-time secret, or get **Trust** in Settings from a browser this Mac already trusts, client/settings-sync.ts), it is for this runner's workspace, and it is not older than the newest version this Mac accepted (`~/.kitebook/policy-<name>.json`: no rollback). An unsigned, tampered, foreign or older policy is ignored and the task asks as before.
- **What "run on its own" means:** a task from that app, in one of those projects, before `until`, that carries a valid signature from a key the policy names for that app (24-hour window, one use per nonce) runs without asking, in any `approve` mode; it never turns on `approve: auto`. Another app, another project, a machine task, an expired entry or a bad signature asks as usual, and the review page says why. Push still asks unless the owner ticked "can push" (and never pushes main); the deploy/spend/send gate, the destructive-command guard, protected files and worktree isolation are unchanged.
- **The app's key:** an app that signs its own tasks (`kitebook keygen`) can be pinned in the policy, which keeps it end-to-end. For apps that can't (Hark, Claude.ai, ChatGPT), the server mints an Ed25519 key per app (`app_key`) and signs that app's tasks only where the signed policy lets it run on its own. That key adds nothing against a compromised Kitebook, which holds it: what bounds such a Kitebook server is the owner-signed policy (that app, those projects, that end date, no push unless ticked).
- **Owner ops:** `/start` POST ops `policy` (read: per workspace the signed policy, each app with what it can do now, each runner's pinned owner-key fingerprints and the version it uses, the projects, the audit list), `policy_set {space, app, envelope, access?, undo_of?, nonce}`, `owner_key {key, label | remove, nonce}`, `app_key {space, app, nonce}`; the same as `/admin/policy|policy_set|owner_key|app_key` with the old master key (`bun client/admin.ts ...`). The runner op `policy` is runners-only and read-only.
- **Approving at the computer:** `kitebook approve` (= `bun runner.ts approve [runner.json]`) lists every run or push ask that waits on this Mac and answers it (`approve <task|code> yes|no`). The runner takes an answer only with the current approval code, and only from the process the OS says holds the answer file open (the CLI keeps it open until the runner replies; a pid written in the file is never trusted), when that process is outside the runner's own process tree and runs in a terminal (a controlling tty, which agents the runner starts don't have). A forged answer file, an answer naming someone else's pid, or one from a pipe is refused and audited. On Windows (no `/proc`, no `lsof`) the CLI listens on a loopback port named in the answer instead of holding the file open, the runner asks the OS who owns that socket (`netstat -ano`), walks parents in the CIM process table (creation times checked, so a reused pid isn't a parent), and "a terminal" means descending from Explorer or Windows Terminal. Like the shims this is a same-user tripwire, not a sandbox: an agent that both detaches from the runner and gives itself a pty (on Windows: gets Explorer to start a program for it) gets past it. The deploy/spend/send gate never takes it.

### Run tasks without asking (autorun) and Experimental

Two separate owner-signed switches. They were one ("dev mode", policy field `dev`) until 2026-10-23; a policy signed before that is read as both (the owner keeps the same permission and gets Experimental), and every new version writes the new fields and never `dev` again. Neither switch implies the other.

**Run tasks without asking** is a permission: one switch instead of per-app rules (the top row of Settings, optional end: 8 h, 24 h, 7 days). It is a field of the same owner-signed policy, `autorun: {on: true, until, keys: ["ed25519:<relay-held autorun key>"]}` (absent = off), so the runner enforces it exactly like the rest: only when a pinned owner key signed it, never rolled back, ignored past `until`.

- **Who it covers:** tasks (and chain steps, and plans promoted to a run) from the owner's own apps: an assistant or coding agent of this account, still connected. The server signs such a task with the autorun key only after checking that (Dir `peerState`: not removed, access not ended); the runner asks the server again per task (op `policy` with `from`) and asks the owner if the sender was removed meanwhile, is a person (`human`) or another runner. An app's own per-project entry still applies where it does (it decides pushing there); an app set to "can't send tasks" stays that way.
- **What it doesn't change:** an app's folders (it never widens what an app can read or write), the guard, the deploy / payment / email gate, worktree isolation. Pushing: the runner pushes only the task's own branch, and under autorun it does so without asking where the project says "ask"; a push to the default branch or a force push is never done by itself (`autorunPushOk`; the runner never pushes the default branch and the guard blocks the agent from it). A project set to never push still never pushes.
- **Who can turn it on:** only the owner, in a signed-in browser (session + one-time nonce + the browser's owner key + the presence check). Apps get the read-only `experimental` op (old name `dev_mode`), which reports it as `autorun`; passing `set` is refused (403) and listed in Settings -> Recent changes. A change that touches an app, autorun or Experimental is refused if it also changes another of them ("one change at a time"), so no page turns a switch off by accident.
- **What it adds against a compromised Kitebook:** the autorun key is relay-held like the app keys (kept as `appkey:*autorun`; a Kitebook from before the rename copies its old `*dev` key once so signed policies keep working), so while it is on a compromised Kitebook could sign a task under any app name it likes (with app keys, only for the apps the policy names). The owner's signature still bounds it to "on, until then". Turn it off, or use per-app rules, when that matters.
- **Visible:** a "Running your apps' tasks without asking · Turn off" banner on Get started and Settings; each task that ran this way says "ran without asking", and the runner's audit log has a `policy_auto` entry with `autorun: true` for every one.

**Experimental** (Settings -> More -> Experimental) turns on features that aren't finished, and nothing else: no permission, no approval, no update rule changes with it (approvals, Run tasks without asking and "Let apps update Kitebook" are their own settings). Policy field `experimental: {on: true, ci?: bool, gh_status?: bool}` (absent = off), signed like the rest; turning it on asks for presence, off never does. What it turns on:

- **Recent logs and errors (`relay_logs`):** the server keeps every unhandled error and 500 (route, status, message, stack, request id) per account, and the runner keeps its own lines in `~/.kitebook/logs/devlog.jsonl` (0600); both redact before storing (client/redact.ts `redactLog`: tokens, Authorization / Cookie headers, `?token=`-style values, Kitebook tokens, emails, plus the runner's token and agent env values and the server's own secret env / .dev.vars values) and cap the ring. Only the owner's Mac (`kitebook logs --errors`) and Settings read it with Experimental off; while it's on, also the owner's own connected apps with dispatch rights (checked live, like autorun; never a person or another Mac), and the runner sends its lines to the server. Turning Experimental off stops both.
- **Update to dev now:** with Experimental on, Settings -> Updates offers it for a Mac that runs from a git checkout: an owner-signed change (do `update_ref`, `ref` only `dev` or `main`: the button sends `dev`, an older page sends `main`; any other branch is refused by the server and again by the Mac), done only while the policy the Mac verifies itself has Experimental on, only as a fast-forward to `origin/<ref>` (pinned for that one update), replacing the terminal y/N for that case.
- **Server upgrade inside an update:** an update the owner approved (Update to dev now, or Update to main now on an older Settings page, `kitebook update`, a `kitebook pin`ned commit) also upgrades a Mac server still on `cf dev` (`scripts/upgrade-mac-host.sh`, run by the runner or the owner's own `kitebook` process, never a task). The new code (`client/host-upgrade.ts`) starts it only for the exact commit the checkout runs and only with the owner's approval of it, newer than the last try: `updatePin` == HEAD, or an audit entry by `owner cli` (update / fast-forward) or `update_ref` (the signed Settings click) to HEAD. A task's process (`KITEBOOK_TASK_ID`) is refused; an agent's restart or its own update (audited as `task ...`) carries no approval. Like every local file check, this is about Kitebook's own paths (ops, MCP, kitebook-svc, tasks); an agent running unconfined as the same macOS user is outside it.
- **Local CI (Test every push):** the runner runs a project's own test command (`kitebook.json` `{"ci": "<cmd>"}`, else package.json `test`; none = skipped) in a throwaway `git worktree --detach` of the exact commit, at low priority (`nice -n 10`), with a timeout (20 min), one run per machine, and cancels a superseded run of the same branch. Triggers: a new commit on a watched branch (fetched from the project's own `origin` only; default its `dev` branch), a task branch when its task ends, and Run tests / `ci_run` (the owner, or the owner's own connected apps with task rights, checked live). It never runs a fork: pull-request refs, other remotes and anything but a plain branch name are refused. The test command is the repo's own code, run like the task verify step already does, under the same OS user. Results (pass/fail, counts, seconds, last 20 lines) go to the server (`ci_report`), an audit line `ci_run` per run; a GitHub commit status only with **Show test results on GitHub** on (off by default) and a token already on the Mac (`GH_TOKEN` / `GITHUB_TOKEN` / `gh auth token`). A commit status never starts a workflow; no GitHub Actions minutes are used.
- **CLI:** `kitebook experimental status` (old name `kitebook dev`; checked against the browsers this Mac trusts) says how both switches stand; `kitebook experimental on|off` opens Settings.

### The built-in tunnel (no server / domain)

A Kitebook server self-hosted on a Mac with "No server / domain" (`scripts/mac-host.sh`, `client/tunnel.ts`) is reached through a Cloudflare tunnel that only forwards HTTPS to `http://127.0.0.1:<port>`; nothing listens on another interface and no router port opens. The same sign-in applies as anywhere: `/admin` needs the admin token (the tunnel helper reads it from the server's `.dev.vars` and talks to the server over the local port only), ops need a token, pages need the owner's session. cloudflared is the one on the owner's PATH or a pinned release whose archive and binary sha256 are checked before it runs. Settings → Connection is the operator's (root account) only: Restart tunnel and the tunnel token need the session and a one-time nonce; the token is handed to the Mac once and not kept by the server, reaches cloudflared in its environment (never a command line or a log), and stays in `~/.kitebook/tunnel.json` (mode 600, a folder agents can't touch). Other accounts on the server see only the address.

### Ingress lockdown (what the public address shows)

The self-hosted server listens twice, both on 127.0.0.1 (`selfhost/config.capnp`, `scripts/serve.sh`): **local** on the server port (7820: this computer's runner, coding agents and its own browser) and **edge** on the port after it (7821: the only one a tunnel or reverse proxy should point at; the built-in tunnel, ngrok and Tailscale Funnel setups do). Each listener stamps every request (`x-kitebook-ingress`), and workerd drops whatever value the client sent, so the stamp can't be forged. Kitebook never trusts 127.0.0.1, `Host` or `X-Forwarded-*` to mean "local": cloudflared and local agents connect from 127.0.0.1 too. Those headers can only make a request count as public (a public `Host` or any proxy header on the local port, for a tunnel still pointed there or a DNS-rebinding page).

With the lockdown on, the public edge serves only `/mcp` and `/v1` (token in the `Authorization` header), the OAuth endpoints and metadata, the sign-in step of an OAuth connection, `/health`, `/open` (device-signed `kitebook open` links), the agent docs (`/llms.txt`, `/openapi.json`), the runner installer, invite links, and the code-and-poll endpoints of `kitebook join` / `kitebook login <url>` (`/join/start|poll`, `/claim`, `/claim/start|poll`: the new machine's device key signs its polls and an owner device or the server shell approves). A remote server that is still unclaimed answers that same 404 from the edge for everything but `/health` and `/claim`. Everything else, including `/start`, `/settings`, `/admin` (even with the recovery code), `/approve` pages and `/device`, answers the same 404 as an unknown path unless the request carries the owner's browser session. It changes no credential check: it only hides routes from the public. `?token=` links are gone everywhere: a token in a URL lands in proxy, tunnel and browser logs, so a request that still sends one gets a 401 saying to send the header.

The setting (`ingress.lockdown`, per account and tenant): on for a new install; an install from before keeps its public dashboard ("auto") until an owner device exists, so an update never locks anyone out. Settings -> Connection shows the state and which listener the page came in on. Turning it on works anywhere; turning it off only on this computer's own page (the local listener) or with `kitebook admin ingress on|off|auto` from the server shell. A Kitebook with public signup (`OPEN_SIGNUP` / `HOSTED`) keeps its signup page public. On Cloudflare Workers there is no local listener, so the lockdown waits for an owner device.

## Approving from another device with the master password

Settings -> More -> **Approve from other devices with my password** (on by default; turning it on or off asks for presence). When an approval page is opened somewhere other than the Mac (a phone: the `/device` link an agent shows after `POST /connect`, or a "confirm it's you" prompt in Settings, consent or join), the browser can't reach the Mac's loopback helper, so the typed master password goes to the Mac another way:

- **The path it travels.** Browser -> HTTPS -> your Kitebook's public address (with a Cloudflare tunnel, Cloudflare's edge terminates TLS and forwards it through the tunnel) -> the Kitebook server -> the Mac runner's existing outbound connection. So the password is readable, in memory, by the server process and, with a tunnel, by Cloudflare's edge, exactly as the rest of that page's traffic is. Use this only on a Kitebook you run (or trust) and, if that matters to you, a direct-TLS address instead of a tunnel.
- **Where it is checked.** On the Mac only. The server never verifies a password and has no hash: it holds the typed password in memory for that one request (at most 20 s; wiped as the runner takes it), never writes it to storage, logs or events (the `presence.remote` event carries only a request id, and only that runner sees it). The runner unlocks its own Argon2id-wrapped password key with it, signs exactly that approval (`device_grant:<code>` or `confirm:<code>`, nothing else), answers with that signature and forgets the password. The server checks the signature like any other presence assertion.
- **Limits.** Only the owner's own approvals that already take the master password. 5 wrong passwords for one approval end its remote tries; 5 wrong in 15 minutes (any approval) lock remote password approval for 15 minutes (recent tries are listed in Settings). The Mac adds its usual growing waits (three typos free, then 30 s, 1 min ...). 20 tries per address per hour on the page. `kitebook approve` and the page opened on the Mac keep working during a lock.
- **Mac offline.** The page says your Mac didn't answer; nothing is approved. Approve when it's back.
- **Off.** Turn the switch off, or put `"remotePassword": false` in the Mac's runner.json; then the password is only ever typed on the Mac.

**A phone's passkey as an approval device.** Open `/device?add=passkey` on the phone (linked from the approval page and Settings -> More -> Approve from other devices) and add a passkey: a WebAuthn credential made by the phone's platform authenticator for this Kitebook's address, unlocked with the phone's own PIN, password, fingerprint or face. It approves nothing until you approve its code once: with your master password (typed there, checked by your Mac as above) or `kitebook approve <code>` on the Mac. The server keeps only its public key, as an owner device (Settings -> Devices, "Phone passkey"; Revoke ends it). Each approval with it answers a single-use challenge (2 minutes) bound to exactly that approval (`device_grant:<code>` or `confirm:<code>`), and is accepted only for this address (rpId hash and page origin), with user verification, and a signature from an active passkey device; a signature counter that goes backwards is refused. The phone's page then offers "Approve with passkey" first and the master password as the fallback. Attestation is not checked (`none`): what makes the passkey trusted is your approval of its code, not its maker. It is separate from the sign-in passkey (Passkeys and browsers).

## Connecting without the key

The old master key is now a recovery code: no normal path asks for it (sign-in, signup, the consent and device pages).

- **Sessions (Better Auth).** Every way in (`kitebook open`, a passkey, a sign-in request, the recovery code) ends in one Better Auth session: an HttpOnly, SameSite=Lax cookie `kitebook-<acct>.session_token` (`__Secure-` on https), 30 days, sliding. It counts as the owner on /start, /settings, the consent and /device pages and owner-only review pages. Settings → Devices & passkeys lists the browsers signed in and signs any of them out at once. There is no second "remembered browser" cookie any more.
- **`kitebook open`.** The CLI asks the running runner through `~/.kitebook/asks/open.<pid>.req`; the runner refuses a request from a process it started (the same ancestry tripwire as `kitebook approve`), then calls the runner-only op `login_link` for a single-use link valid 5 minutes (`LOGIN_LINK_TTL`). The secret is in the URL fragment (`/start#login=ll.<acct>.<secret>&trust=<k>`), so it is never in a request line, a proxy log or a referrer; the page posts the first half once (`link_signin`). Reuse or expiry answers 410. `k` never reaches the server: the browser proves it holds it (HMAC over its signing key) and the Mac then trusts that browser by itself, so nobody pins a key by hand. Anyone holding the runner's token can make such a link: the runner token is an owner credential.
- **Passkeys.** Better Auth's passkey plugin (SimpleWebAuthn underneath): added from a browser signed in today, attestation "none", any authenticator (phone via QR, laptop, password manager, security key), discoverable, so sign-in needs no account name on a self-hosted Kitebook. Passkeys from before the update can't be carried over (different credential store and user handle): Settings asks once to add the passkey again.
- **Sign-in requests.** A browser that isn't signed in can ask (`login_ask` on /start). It gets a code like `BCDF-GHJK`, lives 5 minutes (`OAUTH_CONNECT_TTL`), is decided once, and is bound to that page's own secret (the poll token). Only runners of that workspace may read (`connect_get`) or answer (`connect_decide`, bound to the request's nonce) it, and the runner asks with `kitebook approve <code>` on the Mac; a browser already signed in can also approve it (Settings). Nothing is pushed to the phone for signing in.
- **Apps connecting (OAuth 2.1 on Better Auth).** PKCE S256, RFC 8252 loopback redirects, refresh rotation, RFC 7009 revoke; apps identify themselves with a Client ID Metadata Document (the https URL of their details) or dynamic registration (OAUTH_DCR rules below). Kitebook keeps the policy: its consent page writes a grant (the app's connection, its space, its verbs) and every call on `/mcp`, `/v1`, the WebSocket and events checks it, so removing an app stops a still-valid access token at once and ends its event streams. Better Auth's own consent memory is switched off: the owner is asked every time unless the app has a grant listed in Settings. One app installed on two computers (one CIMD client id) joins the same connection; removing it signs both out.
- **CIMD fetch (SSRF).** The server fetches an app's metadata document only from https on a public host name: localhost/.local/.internal names, private, loopback and link-local IP literals are refused, every address the name resolves to (DNS over HTTPS) must be public, and redirects aren't followed. A name that resolves to localhost is refused before any fetch. (A DNS answer that changes between the check and the fetch is the residual gap; Cloudflare's own network doesn't route to private ranges, and a self-hoster can add a public-only outbound network to the workerd config.)
- **Names.** A name in use never blocks a connection: the same app connecting again replaces its old OAuth connection by default (its tokens and event streams end), anything else (a token connection, a revoked one, or "keep both") gets the next free name.
- **What was granted** is shown on the consent page after approval, returned to the page (`granted`) and to the app (`whoami.can`), in the same words. Delete is never part of a default choice.
- Error texts for agents never mention the key: a missing send-tasks permission says to sign the app in again choosing "run tasks", or Permissions on /start.

## Quick asks and steering (what holds today)
- **Quick-ask sandbox.** A quick ask runs the agent in the project's checkout under the OS sandbox (`client/runner-ask.ts`): macOS `sandbox-exec`, Linux user + mount namespaces. It can't read credentials (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/.kitebook`, `~/.docker`, `~/.kube`, `~/.netrc`, `~/.git-credentials`, `~/.npmrc`) or the checkout's `.env*` files, and can't write anywhere in your home folder (the checkout, shell rc files, LaunchAgents) except the agents' own state folders (`~/.claude`, `~/.pi`, `~/.codex`, caches), and not even there to their settings, hooks or instruction files. Temp stays writable. **The network stays open**: the agent has to reach its own model API, so "don't use the network" is a request in its prompt, not a control. With no OS sandbox the before/after git check is all there is, and it can't see writes to gitignored files or outside the checkout. Asks to an agent with no read-only mode of its own (Grok) need your approval even from your own apps (`"askAutoAnyAgent": true` opts out).
- **Steering after approval.** A `task_steer` note is new instructions added after you approved the task. It reaches the agent without asking you only when you wrote it (/start), or the task ran without asking under your own standing choice (Run tasks without asking, a permission, `approve: auto` for unsigned trusted senders). On a task you approved by hand, and on a signed auto-run (the signature covers the task, not text added later), the runner asks you again with the note shown (gate `steer`, the same payload binding and ways as any approval); a no, or no answer, marks it refused (`task_get.steers[].refused_at`, thread.md, the audit log) and the agent never sees it.
