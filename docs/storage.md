# Storage, self-hosting, moving between hosts

- **Per space:** one Durable Object holds content-addressed blobs (sha256), linear changesets, the current tree, tasks and the event log. A single writer means commits never race.
- **Big/binary files** (over 256 KB, and binaries; up to 25 MB each) go to a blob store. It's auto-detected, or pinned with `BLOB_STORE=r2|disk|s3|inline` (an explicit choice that isn't configured is an error, never a silent fallback). The selector isn't named `BLOBS` because that's the R2 binding.

  | Where Kitebook runs | Blobs live in | Setup |
  |---|---|---|
  | Cloudflare (`cf deploy`) | R2 bucket binding `BLOBS` | none (cloudflare.config.ts) |
  | Always-on Mac (`scripts/mac-host.sh` -> `scripts/serve.sh`: the built bundle on plain workerd) | **local disk**: `~/.kitebook-server/blobs/<sha256>` (`KITEBOOK_DATA` overrides) | none |
  | Development (`npx cf dev`, this machine only) | **local disk**: the R2 binding is simulated under `.relay-data/` | none |
  | Plain workerd, no Cloudflare ([selfhost/config.capnp](../selfhost/config.capnp)) | **local disk**: `.relay-data/blobs/<sha256>` via workerd's writable disk service bound as `BLOB_DISK` | `npx cf build`, then `npx workerd serve selfhost/config.capnp --experimental` |
  | Optional anywhere: S3-compatible (MinIO, Backblaze B2, AWS S3, R2's S3 API) | your bucket, keys `blobs/<sha256>` | `BLOB_STORE=s3` + `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` (optional `S3_REGION`) |
  | None of these | inline in DO SQLite | 1.5 MB file cap |

  Auto-detect order: R2 binding, then `BLOB_DISK`, then complete `S3_*` vars, else inline. Every read re-hashes the bytes against the sha, so a torn or edited blob file is refused (error), not served.
- **Local data folder:** the Mac self-host (`scripts/serve.sh`) keeps its state in `~/.kitebook-server/` (mode 700, `do/` + `blobs/`; `KITEBOOK_DATA` overrides), outside the project folder, so nothing that serves the project can serve the data. `mac-host.sh` copies an older install's `cf dev` state over once (`scripts/migrate-cfdev.ts`: Durable Object SQLite as is, the simulated R2 bucket to `blobs/<sha256>` with every hash checked) and moves the old folder to `~/.kitebook-server/cf-dev-backup-<date>`. For development, `cf dev` keeps all state (Durable Objects + the simulated R2 bucket) in `.relay-data/` in the checkout (`KITEBOOK_DATA=/path` overrides). Older checkouts used `.cloudflare/state`; it's still used if `.relay-data/` doesn't exist, and `mac-host.sh` moves it over once. The workerd sample uses `.relay-data/do` and `.relay-data/blobs`. Back up by copying the folder while the server is stopped.
- **Self-host:** run the same Worker on workerd (Docker or any VPS) with [selfhost/config.capnp](../selfhost/config.capnp): DOs and blobs on local disk, recovery code from `KITEBOOK_ADMIN_TOKEN`, listening on 127.0.0.1:7820 (local: the dashboard) and 127.0.0.1:7821 (the public edge; put TLS/tunnel in front of 7821 only, see [security](security.md#ingress-lockdown-what-the-public-address-shows); it must send `X-Forwarded-Proto: https`, as cloudflared and common reverse proxies do, so sign-in sees the https address: without it, passkey and app sign-in answer "needs https"). It's single-machine, so back it up yourself.
- **Move a project between hosts:** `admin.ts export <space> > space.json`, then `admin.ts import <space> space.json` on the other host. External blobs (R2/disk/S3) are carried inside the file and re-homed into the new host's store. The knowledge-base index is rebuilt from the `kb/` files on import. This is the way to go between `cf dev` and plain workerd (the simulated R2 bucket uses its own file format).
- **Switch blob backends in place (copy-over):** blobs are content-addressed and every backend uses the same names, so stop the server, copy the objects across (S3/R2 `blobs/<sha>` -> `.relay-data/blobs/<sha>`, e.g. `aws s3 cp --recursive s3://bucket/blobs/ .relay-data/blobs/` or `mc mirror`; the reverse for disk -> S3), switch `BLOB_STORE`, start it. Files keep their old `storage` label in `stat`; any configured store serves any external blob, and the hash check catches a bad copy.

- **Storage hygiene and limits** (all per space, all with safe defaults):
  - Events are indexed by `(task_id, seq)`, so loading a task never scans the log. The log is also capped by count: 100000 events by default (`EVENTS_MAX`, or `admin.ts retention <space> - <events_max>`; 0 = no cap). The oldest events go first, and an active task's events are always kept. The KB (`kb/`, `context/` and the `kb_*` index) is not in the log, so a trim can't touch it.
  - Task threads and progress (`task_message`, `task_progress`, answers) are stored as rows, not re-committed files. `read tasks/<id>/thread.md` (and `progress.md`) still return the same markdown, and the rows are deleted with the task at retention.
  - `grep` reads one file at a time and stops at a byte budget: 8 MB per call by default (`GREP_BUDGET_BYTES`; `max_bytes` can only lower it). A search that hits the budget returns `budget_exhausted` and `next_after`; call again with `after` to continue.
  - Per-token rate limit: 600 requests a minute per token (a peer token or one OAuth grant) in each space by default (`RATE_PER_MIN`, or `admin.ts ratelimit <space> [per_min] [peer]`; 0 = off). Over the limit you get HTTP 429 with `Retry-After` and a message that gives the limit and how to raise it. MCP Events calls get `ResourceExhausted`.
  - Blob GC (mark and sweep, run by the space's alarm): a blob is kept while any file version points at it (the current tree, the kept history, and always every `kb/` and `context/` version) or an export is reading it. Unreferenced blobs are marked first and deleted only if they are still unreferenced after a grace period: one day by default (`BLOB_GC_GRACE_SEC`, or `admin.ts retention <space> - - - <gc_grace_sec>`), so a client that just asked `has` and commits by sha, or a re-upload of the same content, never loses its blob. Uploads whose commit never landed (a conflict, a quota refusal, a crash) are orphans in R2/disk/S3 and are collected the same way. The blob store is shared by every space on the server, so each space that holds an object keeps a marker `refs/<sha>/<space key>` next to it; GC removes only its own marker and deletes the object once no marker is left. `admin.ts gc <space> [grace_sec]` runs it now (`0` = sweep now). `admin.ts usage` shows bytes freed per space, and `admin.ts prune <space> <older_than_sec>` also caps the grace at that window. Operators can audit the whole store with `admin.ts gc_store` (objects no space marks, such as ones stored before markers existed); `admin.ts gc_store delete` removes them once every account's spaces have been used since the upgrade (each space writes its markers when it first wakes).
  - `repos/**` keeps only the current tree plus a bounded history: the newest version of each file and 10 earlier ones by default (`REPOS_HISTORY`, or `admin.ts retention <space> - - <repos_history>`; `0` = current tree only). Git holds the real history, so older mirror versions are trimmed as new ones are written and their blobs go through blob GC. `kb/` and `context/` are never trimmed.
  - Held-seconds cap: a task can be held (claimed, awaiting approval or running) for at most 24 hours per attempt (`MAX_HELD_SEC`; 0 = off). Time in `needs_input` doesn't count. A task can set a lower cap with `limits.max_held_sec`. Over the cap, the task fails with reason `held_cap` and isn't retried, and the runner stops the agent. This catches a runner that stays online, so its lease never expires, while the task never finishes.

## Self-host on an always-on Mac (no server or domain needed)

```bash
brew install node oven-sh/bun/bun
./scripts/mac-host.sh                  # server at login, then it asks how assistants reach the Mac:
                                       #   1) No server / domain (recommended): Kitebook's built-in tunnel -> https://<words>.trycloudflare.com
                                       #   2) Tailscale Funnel -> https://<mac>.<tailnet>.ts.net   3) ngrok (NGROK_DOMAIN)
./scripts/mac-host.sh status | uninstall
```
**No server / domain** (`client/tunnel.ts`, the default when there's no terminal; `KITEBOOK_TUNNEL=quick|tailscale|ngrok` answers ahead of time and the answer is kept in `.kitebook-tunnel`): a small helper runs a Cloudflare quick tunnel to Kitebook's public edge listener, normally `http://127.0.0.1:7821`. Local agents and the dashboard use port 7820. It uses cloudflared from PATH or downloads a pinned release and checks its archive and binary sha256. No Cloudflare account is required for a quick tunnel. The helper restarts cloudflared when it stops and reports the address and health in **Settings → Connection**. A quick tunnel's URL changes on restart; update assistants that used its old address. For a stable named tunnel, follow the [domain walkthrough](domain.md): route the hostname to the public listener, then paste the connector token and hostname into Settings. The token stays privately on the Mac in `~/.kitebook/tunnel.json` (mode 600), never in a command line or server storage. `kitebook tunnel quick` switches back. Manage the helper with `kitebook status`, `kitebook tunnel`, `kitebook restart|stop|start tunnel` and `kitebook logs tunnel`. App operations still require their existing authentication; public access does not grant workspace access.

It then opens `<url>/start` in your browser, signed in (a one-time 5-minute link; no key to copy), and you run the **Connect your Mac** line on the same Mac (`curl -fsSL <url>/install.sh | sh -s -- <invite>`): it fetches the runner into `~/.kitebook/client`, runs `init` (safe defaults, `requireSignedAuto: true`) and starts it at login. `bun ~/.kitebook/client/runner.ts doctor ~/.kitebook/runner.json` checks it. With no Tailscale, `NGROK_DOMAIN=<your-static>.ngrok-free.app ./scripts/mac-host.sh` uses ngrok's free static domain.
Everything stays on the Mac: spaces, tasks and big files live in `~/.kitebook-server/` (S3 only if you set it up). The server is plain workerd running the built bundle (`scripts/serve.sh`, rebuilt when the sources are newer), never Vite: a dev server would also serve the project folder through the tunnel. You can use cloudflared, ngrok or a reverse proxy, subject to the assistant's hostname and transport restrictions. The built-in quick tunnel needs no account; Funnel or a named Cloudflare tunnel can provide a stable address while that hostname remains configured. See [connection compatibility](setup.md#address-compatibility-and-avoiding-a-domain). (`KITEBOOK_ALLOWED_HOSTS=kitebook.example.com` only lets the local `cf dev` development server answer a name besides localhost; never put it behind a public tunnel.)

## Cost and Durable Object boundaries

The cloud deployment stores account/workspace state in Durable Objects. Self-hosting on the Mac uses local workerd; check which deployment you run before attributing costs. [Cloudflare charges for requests, duration and storage](https://developers.cloudflare.com/durable-objects/platform/pricing/). A [per-invocation CPU limit](https://developers.cloudflare.com/durable-objects/platform/limits/) is not an account spending cap: many short invocations, alarms, streams or writes still accumulate costs.

Cloud objects wake for requests, messages and scheduled alarms, then can hibernate; the server existing does not keep every object running. Timers, pending I/O and streams can prevent hibernation ([lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)). Kitebook uses hibernatable runner WebSockets and platform ping/pong auto-responses. SSE streams intentionally remain active, but have duration/count limits. Normal heartbeats/advertisements still make authenticated requests. The default 30-second heartbeat alone sends 86,400 reports in 30 days; each HTTP report authenticates against Dir and then calls Space, with additional traffic from advertisements, knowledge sync and tasks. Treat that as a request-count illustration, not an invoice estimate. Per-token request limits reduce work inside the object; rejected requests and authentication can still incur platform usage. Prefer events and bounded long-polls, and check MCP revisions at lifecycle boundaries rather than every few seconds.

Task retries are capped (default one, explicit maximum five). Webhook failures, including unexpected delivery exceptions, consume a finite retry budget (default eight; termination notices three), with exponential backoff and a batch ceiling. Failed external blob cleanup preserves a retry marker at least a minute in the future. Alarm deadlines are finite and overdue work has a one-second floor; no alarm should continually rearm for poisoned rows at the current instant. These controls reduce runaway paths; they do not prove every possible loop absent.

For paid cloud deployments, review request/duration/storage usage and configure the account's available usage notifications. Notifications are not a hard cutoff. A genuinely bounded total bill needs a verified provider-enforced budget/limit or an operational shutdown policy; Kitebook does not claim to provide one. This change does not modify the owner's plan, deployment or billing settings.

## Failure-driven resource guard

[`client/resource-guard.ts`](../client/resource-guard.ts) defines the shared failure budgets, request deadlines and stream bounds. The runner API transport, outbound webhooks, S3 operations and SSE lifecycle use it. Durable counters live in each workspace's existing SQLite metadata, not a separate service.

- Approval delivery stops after five failures or one hour. Its separate budget does not reset when the runner restarts. The task shows `approval_retry_paused` and explains that no owner declined it. Fix the approval channel, then use the existing **Retry** action to start a fresh, approval-required task with the original context.
- Unexpected alarm failures back off, then pause after five failures or one hour. A new object instance keeps the circuit state. Webhook deliveries and storage cleanup retain their finite retry budgets. Legacy blob-reference backfill stops after eight failures, shares concurrent calls, and keeps its budget across cold starts.
- An SSE response has at most 256 KiB of queued writes. Graceful shutdown has a one-second deadline; a stalled response is then aborted. Its connection slot remains occupied until completion or abort. Large initial replays finish in pages with an advancing cursor; a single event too large for push returns `use_poll_for_large_event`, which clients should recover through `events/poll`.
- Runner API requests have a 30-second deadline, S3 operations 15 seconds, and webhooks five seconds. Deadlines include response-body consumption. S3's hidden SDK retries are disabled; the workflow owns the retry budget.

Inspect or pause work using the admin CLI (authenticate privately as usual):

```sh
bun client/admin.ts resources main status
bun client/admin.ts resources main pause
bun client/admin.ts resources main resume
# All current and future workspaces of this account:
bun client/admin.ts resources - pause
bun client/admin.ts resources - resume
```

Pause and resume actions are recorded in the account audit log; inspecting status does not add an audit entry. Account and workspace pauses are independent. Resume clears that scope's pause and the alarm/storage/backfill failure circuits; paused approval tasks still need an explicit Retry. Status reports failure counters, pending webhook count and deployment pause state. For an emergency Cloudflare deployment pause, deploy with `KITEBOOK_RESOURCE_GUARD_PAUSED=1`; remove that setting to permit work again. An admin resume cannot override a deployment pause.

The resource pause stops server-owned background work and new task claims. Use the existing task kill switch to cancel coding agents already running. These controls bound the guarded failure-driven workflows started by Kitebook. They are not a spending cap: incoming HTTP requests, intentional connection recovery and normal authenticated activity can still generate usage. They do not cancel external effects already completed.
