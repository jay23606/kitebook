# What Kitebook does

The short version is in the [README](../README.md). Getting started: [quickstart](quickstart.md). Words used on screen: [glossary](glossary.md).

Kitebook runs on Cloudflare Workers + Durable Objects (one SQLite Durable Object per workspace), with R2 for big files. The same code self-hosts on workerd or an always-on Mac ([storage](storage.md)).

## Safe by default
- **Narrow access by default.** Invites from `/start` (Hark) and the CLI examples give an assistant the safe default access: it reads everything and can send tasks, but saves files only in the `shared/` and `kb/` (knowledge base) folders. An app connecting through the consent page (Claude.ai, ChatGPT, `mcp login`) gets the choice you pick there; the recommended one is its own `kb/<name>` folder + send tasks, each of which you approve. Coding agents the installer connects get their own folder and no task sending until you change it in Settings. Your Mac's runner can use `tasks/`, `shared/`, `repos/` and `kb/`. Code goes in through git or a `change` changeset, never as loose files. 
- **Connecting an app needs no key:** when Pi, Codex or Claude Code runs `mcp login kitebook` (or Claude.ai / ChatGPT add the connector), the app signs itself up (a Client ID Metadata Document, or dynamic registration for older apps) and the consent page shows one card: the app, "wants to connect to your Mac", one sentence of what it gets ("Pi can read and edit kb/pi. It can send tasks to your Mac; you approve each one.") and three choices (**Read everything, save to shared memory, send tasks (recommended)**, **Just this folder**, **Read only**); "run tasks on its own" in projects you pick and everything else are under More options, and delete is never in a default. You're asked every time an app connects, unless it still has access listed in Settings. Not signed in yet? The app's sign-in goes to your Kitebook's sign-in page first and comes straight back. Removing an app in Settings stops its sign-in at once, even a token that hasn't expired. A name already in use never blocks you: the same name connecting again replaces its old connection (ticked, so it keeps its name), any other clash takes the next free name (pi-2), and **Rename** is one tap.
- **Signing in needs no key:** run `kitebook open` on your Mac (it opens Kitebook signed in; that browser stays signed in for 30 days and your Mac trusts it by itself), or use a passkey (add one in Settings), or press **Send a sign-in request** and answer it with `kitebook approve <code>` on the Mac (or from a browser already signed in). Sign-in is Better Auth on your Kitebook's own storage ([how it works](AUTH-ARCHITECTURE.md)).
- **Settings, all by click:** `https://<kitebook>/settings` (or `kitebook settings` on your Mac) is one page, on your phone or desktop, light or dark. **Connected apps**: per app what it can do (**Read everything, save to shared memory, send tasks**, the default / **Just its folder** / **Its folder + send tasks** / **Read only**), which folder, the projects it may run tasks on its own in, how long it keeps access (1, 7 or 30 days, or no end date) and **Remove**. **Devices & passkeys**: browsers signed in, passkeys, sign-ins waiting, and which browsers your Mac trusts (**Trust** / **Forget**). **Approvals**: a signed-in browser and your Mac (dialog, `kitebook approve`) always work; **Also send approvals to my phone** is one tick, and the page shows the ntfy name to add with a Copy button. **Releases**: the release key installs check, and **Create release key** on your Mac (the private half stays in its keychain; Copy the public half). **Recovery**: passkey or `kitebook open`, plus an optional printable recovery code. The consent page offers "Let it run tasks on its own in: [projects]" when an app connects, and the review page has **Always allow \<app\> in \<project\>**. Each change that runs on your Mac is signed in your browser (a key that never leaves it) and lands in an audit list with **Undo**; your Mac acts only on changes from a browser it trusts. A browser signed in with `kitebook open` is trusted by itself (a one-time secret in the link that only that browser and your Mac know); any other browser is trusted with one click in a browser your Mac already trusts. Details in [docs/security.md](security.md#standing-permissions).
- **Approve at the computer:** `kitebook approve` lists what waits for you on this Mac and answers it (`kitebook approve <task|code> yes|no`), next to the dialog and the phone.
- **Run tasks without asking, one switch:** the top row of Settings (optionally **Turn off after** 8 hours, 24 hours or 7 days). While it's on, tasks, chain steps and approved plans from your own connected apps (Hark, Pi, Codex, Claude Code, any app you connected) start right away, with no dialog, phone push, terminal y or review page; a banner with **Turn off** stays on Get started and Settings, and each task that ran this way says "ran without asking" (and is in your Mac's audit log). It's part of the permissions your browser signs, so your Mac checks it like any other; nothing to edit in runner.json. Still guarded: people you invited and other Macs (only your assistants and coding agents count), apps you removed or whose access ended (checked live), each app's folders (it never widens them), pushing (only the task's own branch pushes by itself; your main branch and force pushes never do), and the deploy / payment / email checks. Apps and agents can't turn it on or off (an attempt is refused and listed in Settings). It used to be part of "dev mode"; dev mode is now two switches, this one and Experimental, and a Kitebook that had dev mode on keeps this switch as it was and gets Experimental on.
- **Experimental:** Settings -> More -> **Experimental** turns on features that aren't finished yet, each with its own switch, and changes no permission. **Test every push** (on by default once Experimental is on) is local CI: your Mac runs each project's own test command (`kitebook.json` `{"ci": "<cmd>"}`, else package.json `test`; a project with neither is skipped) on every new commit of its dev branch and on each task branch when its task ends, in a throwaway worktree, one run at a time at low priority, newest commit first (an older run of the same branch is cancelled); never on a fork, never with GitHub Actions minutes. The task page shows "tests passed (12)" and a **Run tests** button, Settings -> Experimental lists the latest runs, and assistants use `ci_run` / `ci_status`. **Show test results on GitHub** (off by default) also posts a commit status, with a GitHub token already on your Mac. Experimental also adds **Update to dev now** in Settings -> Updates for a Mac that runs from a git checkout (`dev` is where tested builds land before `main`) and moves an app's `relay_update` to the newest origin/dev commit (otherwise the branch your checkout follows): no confirmation, only a fast-forward to the latest, checked and rolled back if it fails; Settings -> Updates shows who updated it. Don't want apps updating at all? Settings -> Updates -> **Let apps update Kitebook** (its own switch). And it shares **recent errors and logs** with your own apps: every unhandled error and 500 on your Kitebook (sign-in / Better Auth included; a 500 answers JSON with a `request_id`) and your Mac's runner and update lines are kept, secrets redacted, in a capped ring (newest 500 lines and 200 errors per source), and an app with task rights reads them with `relay_logs`. Settings -> Experimental lists the recent errors. With Experimental off apps get `needs_owner`, nothing leaves your Mac, and you read the same list with `kitebook logs --errors`. `kitebook experimental status` on your Mac says how both switches stand.
- **You approve every other coding task** on the Mac dialog or your phone (ntfy, review page, optional passkey). Each approval is bound to the exact payload and expires in 5 minutes. The review page starts with who asked, why it asks (or why a task ran on its own), what it can touch (project, access level, allowed paths, internet, pushing) and the shared notes it gets with their authors.
- **New runners start safe:** `init` writes `approve` = dialog (phone elsewhere), `access` = worktree, push never, and `requireSignedAuto: true`, so even if you later switch to `approve: auto`, only tasks signed by a dispatcher key you trusted run without asking.
- **Protections on underneath** (kill switch, destructive-command guard, deploy/spend/send gate, hash-chained audit log, protected files); only the machine owner can switch one off. See [security](security.md).
- Zero-touch (`approve: auto` + `access: full`) is an explicit owner opt-in on the Mac: [`scripts/zero-touch.sh`](runner.md#zero-touch-opt-in).

## What it does
- **Files:** versioned read/write/patch/batch with `if_match`, history (`log`, `diff`), server-side `grep`, a secret guard.
- **Tasks:** `task_create` to a runner, with `kind`, `agent`/`model` within the owner's prefs, a checkable `spec`, plan-then-`task_promote`, mid-task questions (`needs_input` + `task_answer`), live steering of a running agent (`task_steer`, delivered after the agent's current run, in the same conversation where its CLI resumes; the owner steers from the Status card), `continue_from` follow-ups and cross-agent handoffs, cancel, leases and automatic retries.
- **Eight coding agents:** besides Pi, the runner drives Codex, Claude Code, Gemini CLI, Cursor (`cursor-agent`), GitHub Copilot CLI, opencode and Grok CLI headless in the task's worktree, built from the flags each installed CLI's `--help` lists and checked against the real CLIs in CI (an old version missing a needed flag is reported with the update command by Settings and `doctor`, not half-run). Answers, steering notes and repair rounds continue the agent's own session where its CLI can resume; quick asks use its read-only mode where it has one, else the git check. Settings -> **Coding agents** shows what each Mac has, **Connect** wires one to Kitebook by click, and you pick which agent works on each project. Who's working fills in by itself: the runner reports every agent session it starts (agent, repo, branch, phase). Details and what's verified: [docs/runner.md](runner.md).
- **Quick asks:** `ask {question, to?, project?}` (MCP tool, `kitebook ask "..."`) answers a read-only question about code on the Mac in seconds: no worktree or branch, a read-only agent (a warm Pi / Claude Code session kept 10 min, one per asker and project, or one read-only run of Codex, Gemini, Cursor, Copilot, opencode or Grok) in the checkout under a read-only sandbox (macOS sandbox-exec, Linux namespaces), streamed (`ask_get`). The owner's own apps need no approval; others are asked. If it needs changes, `ask_to_task` (or Run as a task on Status) makes it a normal task.
- **Your coding sessions (off by default):** enable each app in Settings → Assistants, choose projects, then allow reading, continuing copies, or continuing known-idle originals. Starting work either asks each time or follows that saved scope without repeated prompts. General task autorun cannot override this choice. A running or uncertain original is copied; an original outside the saved capability asks once. Reads outside the chosen projects are denied. Both server and computer verify the owner-signed permission. Disconnect cancels the app's work and revokes its tokens while keeping your native sessions and shared knowledge; reconnecting needs new session consent. Transcripts stay on the computer until an allowed read or copy, with secrets redacted. See [session consent](session-consent.md).
- **Chains:** `chain: [{agent, kind, instructions}, ...]` runs code → review → test steps on one branch, stopping at the first failure. You approve the chain once (bound to its definition); a changed step asks again.
- **Checked at dispatch:** `task_create`/`change` refuse a project or agent the target runner doesn't advertise, with the list, instead of a rejection a minute later (an offline runner that never advertised: accepted with a `warning`). The CLI warns about flags an op doesn't take.
- **Git-first:** tasks name `repo` + `base`; results return `branch`, `commit`, `diff_stat`, `compare_url`/`pr_url`. `change` turns an assistant's diff into a `hark/<slug>` branch; `code_status` shows each checkout's state and unmerged assistant branches. Runners push only their own branch. See [git](git.md).
- **Signed tasks:** Ed25519 end-to-end signatures (`kitebook keygen`, `runner.ts trust add`), so `approve: auto` never trusts the server's word; signed chains cover their later steps.
- **Shared knowledge base:** `kb_add` / `kb_search` across assistants and coding agents, stored as `kb/**` markdown, keyword + optional vector search, attached to tasks as `kb_context`; the coding agents' own instructions (Pi AGENTS.md/skills, Codex/Claude Code AGENTS.md/CLAUDE.md, repo AGENTS.md/CONTEXT.md/.cursor rules) sync in automatically (`runner.ts kb detect`); local agents' notes written while the server is down queue in `~/.kitebook-kb/outbox` (or drop markdown in `~/.kitebook-kb/kb-inbox`) and sync on reconnect.
- **Instructions for your assistants (the brief):** one owner-edited text per workspace (`context/assistant.md`, versioned, never pruned) with the standing rules every connected assistant should keep, e.g. "send code work to the Mac named mac, never to pi", "ask before you deploy", "use kitebook commands, never launchctl". Assistants can't forget it: it is appended to the MCP `initialize` instructions (up to 4,000 characters per workspace), opens `describe` (`brief`), and every `task_create` answer carries `brief.etag`, so a client re-reads it (`describe`, or `brief` with `if_none_match`, callable by name) only when it changed. A heading like `## @hark` or `## @claude-ai @chatgpt` (`@assistants`, `@agents`) starts a section only those apps get. Only the owner changes it, in Settings -> Instructions for your assistants (Save, Undo from the file's history, earlier versions); an app with write access sends `brief_propose` and the owner accepts or dismisses the suggestion there. Apps' writes, moves and deletes of the file are refused. Secrets are replaced with [REDACTED] on save, with a warning. A new workspace starts with a sensible default; it stays out of the KB index and out of context packs.
- **Who's working:** `presence` lists every runner and agent session with what it's on, in one plain line each ("Pi on relay-cf · branch hark/x · running tests · 2m"), busy / idle / offline after a missed heartbeat; the same panel is live on `/start`. Runners report it by themselves; a new task or steer wakes an idle runner at once over its socket.
- **Staying in sync:** `inbox` + `ack` (stored cursor, long-poll), `notify`, signed webhooks with a durable outbox, MCP Events (poll, SSE, webhook), the `/v1/stream` WebSocket.
- **Hosted mode:** many separate accounts on one URL, open signup on `/start`, OAuth dynamic client registration, per-account quotas and rate limits, retention with blob GC.
